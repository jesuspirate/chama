# Brief 04 — give on-chain deposit progress a real consumer

Jet, 2026-09-23: "Yes, give it a consumer." Follows brief 01 (sim on-chain).
Verified against `2d613b3b`.

## Where the progress already is, and where it is thrown away

The native bridge already subscribes to Fedimint's deposit state stream and
discards every intermediate state. `native/fedimint-bridge/src/main.rs:1981`,
`await_onchain_deposit`:

```rust
while let Some(update) = updates.next().await {
    match update {
        DepositStateV2::Claimed { btc_deposited, btc_out_point } => { return Ok(…) }
        DepositStateV2::Failed(error) => bail!(…),
        _ => {}          // WaitingForTransaction, WaitingForConfirmation, Confirmed
    }
}
```

So the states exist one line from where they are needed. Nothing above the
bridge can see them: `IFedimintWallet.onchain.awaitDeposit` is a single
long-poll that resolves only on claim, and `native-bridge-adapter.ts:1229`
makes one POST to `/onchain/await-deposit` and waits.

## Build

### 1. Bridge: remember the latest state, expose it

In `await_onchain_deposit`, record each `DepositStateV2` into a per-operation
map before matching. Add `GET /onchain/deposit-status?operationId=…` returning
the latest state:

- `waiting` — address issued, no transaction seen
- `seen` — `WaitingForConfirmation`, with `btcDeposited` and `outpoint`
- `confirmed` — `Confirmed`
- `claimed` — `Claimed`, with amount and outpoint
- `failed` — with the error text

Keep `/onchain/await-deposit` exactly as it is. The status route is additive.

**Do not invent a confirmation count.** `WaitingForConfirmation` carries the
deposited amount and the outpoint, not "3 of 10". If the bridge can compute
confirmations honestly from the client's consensus block height and the
outpoint's inclusion height, expose it as optional; if it cannot, the UI says
"waiting for 10 confirmations" without a counter. A counter that is guessed is
worse than no counter.

### 2. Interface: optional, not required

Add to `IFedimintWallet.onchain`:

```ts
subscribeDeposit?(operationId: string, cb: (p: OnchainDepositProgress) => void): () => void;
```

Optional, because not every wallet implementation will have it. The native
adapter implements it by polling the status route (a few seconds apart, stop
on `claimed`/`failed`, stop on unsubscribe, stop on `cleanup()`).

### 3. Align the sim to production — this matters most

The sim's `subscribeDeposit` currently emits
`pending → mempool → confirming n → confirmed`, including a per-confirmation
counter production cannot produce. Change the sim to emit **the same state
names and fields as the bridge** — `waiting → seen → confirmed → claimed` —
and only emit a count if production does. A rehearsal that shows things the
real app never shows teaches testers to expect them.

Move `subscribeDeposit` off the sim-only `SimWallet` type and onto the shared
interface, so the sim and the native adapter are checked against one contract.

### 4. The consumer: the funding card

On the on-chain rail, once an address is issued, render the state as one
quiet line under the QR, and let the card's existing waiting geometry stay
put as it changes:

- waiting — *"Waiting for your transaction."*
- seen — *"Transaction seen: 2,000 sats. Waiting for 10 confirmations —
  usually about 100 minutes."*
- confirmed / claimed — *"Confirmed. Locking your sats now."*
- failed — the real reason, plain, and what to do.

en/es/fr/sw. If `subscribeDeposit` is absent, render nothing new — the card
behaves exactly as today.

## Tests

- Sim and adapter emit the same state names for the same scenario.
- The card renders each state and does not shift layout between them.
- Unsubscribe and `cleanup()` stop the adapter's polling (no timers left).
- `seen` never renders a confirmation counter unless the source supplied one.

## Verification

Typecheck, tests, build; `node scripts/verify-payment-card.mjs` extended for
the on-chain states at `?sim=1&onchain=slow`. Then one real deposit on the
native build, above the 1,001-sat minimum, watched from address to claim.
