# v6.4.10 brief 04 — Claim to a Fedi LNURL (and one on-chain status fix)

Commit when green; don't push or ship.

## A. Accept a raw LNURL-pay as a claim destination

Fedi hands out a plain `lnurl1…` receive code (LUD-06, not a
`user@domain` Lightning Address). Chama already decodes and resolves it —
`parseRawLnurl`, `resolveRawLnurlToInvoice` in `src/payments/lnurl.ts`,
tested in `tests.ts:13975-14086` — but the picker refuses it on purpose:
`destination-picker-logic.ts:84` returns `claim.errRawLnurl` ("Raw LNURL
isn't supported here"). Turn it on.

1. `destination-picker-logic.ts`: a `lnurl1…` (with or without
   `lightning:`) becomes `{ kind: "lnurl", lnurl }`, resolved at claim time
   through `resolveRawLnurlToInvoice` for the exact claim amount — same flow
   and typed errors as a Lightning Address. Uppercase (from QR) works.
2. Only `payRequest` is accepted (already enforced in
   `fetchLnurlPayMetadataUrl`). A `withdrawRequest` code gets a plain
   sentence: "This code is for taking sats out, not receiving them. In Fedi,
   use Receive → LNURL."
3. **Check the invoice before paying it**, for both LNURL and Lightning
   Address: decode the returned BOLT11 and refuse unless its amount equals
   the requested amount (and it isn't expired). Today `requestLnurlInvoice`
   returns whatever the server sends.
4. Saved destinations: an LNURL can be saved and reused like a Lightning
   Address. Show it shortened (`lnurl1abc…xyz`), never the full string.
5. Scanning: the claim screen's scanner accepts an LNURL QR.
6. Browser CORS: if the fetch fails as a transport error in the browser,
   say "This receive code's server doesn't allow browser requests — paste a
   Lightning invoice instead, or claim in the Chama app." Native routes the
   request through the bridge if it already does so for Lightning Address;
   don't add a new proxy.
7. Remove `claim.errRawLnurl` from all four languages; add the new strings
   in en/es/fr/sw.

Tests: lnurl → invoice for exact amount; amount-mismatch invoice refused;
withdrawRequest refused with the new copy; `LIGHTNING:LNURL1…` uppercase
accepted; saved LNURL round-trips.

Not in scope: LNURL-withdraw for locking. Locking from Fedi already works
by paying the funding invoice (scan the QR in Fedi).

## B. On-chain funding status says "seen" before anything is sent

`OnchainEscrowPanel.tsx` shows `onchain.seenMempool` whenever the funding
note contains "confirm". With no deposit at all the note is "No confirmed
deposit at the escrow address yet." — so the panel claims the deposit was
seen. Drive the line from a real state (waiting / seen / confirmed)
returned by the check, not from matching error text. Also: the 20-second
poll shouldn't flash the "no deposit yet" note as an error each time.
