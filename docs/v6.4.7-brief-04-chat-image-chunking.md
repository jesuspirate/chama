# Brief 04 — chat image chunking, and the wall it hits (runway 3)

Read this one before scheduling it. The feature as specified cannot be built on
the current wire format, and building it anyway would produce arbiter evidence
that silently loses most of itself on three of our four default relays.

Author: Claude. Verified against `bb3d4091`.

## The blocker, measured in the source

Every escrow event tags `["d", escrowId]` — `TAGS.ESCROW_ID` is literally `"d"`
(`src/escrow-engine/types.ts:204`), and the CHAT publish path uses it
(`escrow-client.ts:2562-2568`). CHAT is kind 38108, inside the addressable
range 30000–39999, where a conforming relay keeps only the newest event per
`(pubkey, kind, d)`.

So **every CHAT event a given author writes for a given escrow shares one
addressable coordinate.** On a relay that performs replacement, an author's
chat history for a trade collapses to their most recent message.

The September retention probe already measured this behaviour on
`nos.lol`, `nostr.mom` and `primal.net`; `relay.chama.community` retains
collisions. `docs/escrow-retention-migration-brief.md` names it.

Two consequences, and the first is the one that matters today:

1. **Chat evidence is already not durable** on the three default public relays,
   before any chunking work. A dispute that relies on scrollback is relying on
   the community relay alone. That is a live finding and it belongs in the
   readiness doc's row 2 regardless of whether chunking is ever built.
2. **Chunking multiplies the failure.** An image split into N events written by
   one author to one escrow produces N events at one coordinate. A replacing
   relay serves back one. The reassembler would then correctly report the image
   as incomplete — forever, on most relays — which is worse than today's
   single-event image, because today's at least arrives whole where it arrives
   at all.

## Therefore

**Do not implement chunking on the current wire format.** It is blocked on
`docs/escrow-retention-migration-brief.md` — the per-event discriminator in `d`
(or ordinary non-replaceable kinds), reader-first rollout, fleet compatibility
measured. That migration is money-bearing and is explicitly not a 6.4.7 item.

What belongs in 6.4.7 is the part that is real now:

### 4.7a — Record the finding

Add to `docs/v6.5-readiness.md` row 2, and to runway item 3, a short measured
statement: chat events share `(pubkey, 38108, escrowId)`, so per-author chat
history is subject to addressable replacement on replacing relays; evidence
durability for disputes currently depends on the community relay. Cite
`types.ts:204` and `escrow-client.ts:2562`.

### 4.7b — Stop the silent part

The publish path already fails loudly on oversize
(`escrow-client.ts:2555`, `MAX_CHAT_EVENT_CONTENT_BYTES`) — that guard is good
and was hard-won. What it does not do is tell the user that an image which
*sent fine* may not be readable by the counterparty later from a public relay.
Add a one-line, non-alarming note on the chat attachment surface when the
preferred relay is not in the connected set: evidence is best kept where both
parties can re-read it. Copy in en/es/fr/sw.

### 4.7c — Leave the encoder alone

`prepareChatImage` (`ChatPanel.tsx:144`), WebP-first at 960px into
`MAX_CHAT_IMAGE_DATA_URL_CHARS = 26_000` (`ChatPanel.tsx:78-79`), is the right
compromise inside a single-event budget and should not be touched in this pass.
Raising legibility further is exactly what needs the multi-event format.

## When the migration lands, the chunking design is

Recorded here so it is not re-derived later. A chunked attachment is N CHAT
events sharing an `imageId`, each carrying `{ imageId, index, total, sha256 }`
of the whole, plus the per-recipient NIP-44 envelope fan-out that already
exists. The reassembler must handle out-of-order arrival, duplicates, and gaps,
and must render what arrived with the missing regions explicitly marked — never
a silently truncated image, which is the failure mode that makes evidence
misleading rather than merely incomplete. The `sha256` of the whole is what
makes a reassembled image quotable in a dispute.

## Recommendation

Take 4.7a and 4.7b in 6.4.7 (both small). Schedule real chunking behind the
retention migration, and do not let it be described as "coming in 6.5" in any
copy or release note until that migration has a plan with fleet numbers behind
it.
