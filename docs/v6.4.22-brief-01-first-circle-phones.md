## A. "your seat: locked" is invisible on the circle card

`TradeCard.tsx` builds `mineText` from `circle.yourSeatLocked`,
`yourSeatClaimNow`, `yourSeatClaimed` and joins it to the claim summary
with " · " in body colour. On the Browse circle card the one fact the
member cares about reads like a footnote.

Make it a state chip, same family as the HOST badge on the same card:

| State | Chip |
|---|---|
| locked | green fill `${T.green}22`, green border, text "Locked ✓" |
| collect now | accent fill, text "Collect now", the only one that may pulse |
| claimed | muted green, text "Claimed ✓" |
| seat reserved, not locked | neutral outline, text "Seat held" |

Chip sits on the title line after the name, before HOST. Claim summary
stays where it is. One chip per card, never two. Test: four fixtures
in `brief-6419.tests.tsx`'s sibling for 6.4.22, 390px, light and dark.

## B. Filter chips scroll to their results

On Circles (and Browse), tapping a chip filters the list but the list
starts below the fold on a phone, so the tap looks like nothing
happened. `CircleCanvas.tsx` already owns a scroll hook
(`main.scrollTop = 0` on step change); extend the idea:

- After a chip changes the filter and the results have rendered, if
  the results header is below the viewport, `scrollIntoView({ block:
  "start", behavior: "smooth" })` on the header. If it is already
  visible, do nothing.
- Never on initial load; only on a user tap. Respect
  `prefers-reduced-motion` (instant instead of smooth).
- Same rule for every chip and the ★ chip, on Circles and Browse.
- Empty result: scroll to the empty-state card, which must say which
  chip produced it.

Test: chip tap with results below the fold scrolls; chip tap with
results visible does not; reduced-motion uses `behavior: "auto"`.

## C. Live listings, the way circles are live

Circles appear on the canvas as their events arrive. Trades do not;
Browse is fetch-on-demand. Give listings the same subscription, with
one rule: nothing moves under a thumb.

- Keep an open relay subscription for kind 38100 scoped to the current
  Browse filter (community, category, rail). Re-subscribe when the
  filter changes; close it when Browse is not mounted.
- A new CREATE that matches the filter is held in a pending set. If
  the list is scrolled to the top, insert it at the top with the usual
  entrance motion. Otherwise show a pill above the list: "3 new
  listings" (n, singular/plural, four languages). Tapping the pill
  inserts them and scrolls to the top.
- A CREATE that does not match the current filter is counted into the
  chip counts (`browse` C in 6.4.17 already counts the scope) but not
  shown.
- De-dupe against the durable cache by event id. The 6.4.x sim-tag
  rule applies: sim-tagged events never reach a non-sim shelf.
- No new notification. The shade already has "New listing"; this is
  the list keeping up with it.

Test: a CREATE arriving while scrolled down produces the pill and no
list shift; at the top it inserts; a non-matching CREATE changes a chip
count only.

## D. The key is never offered for saving on iOS Safari — enforce it

Jet, iPhone Safari (iOS 26), 2026-10-03: created a new key, did not
copy it, landed on Browse. No Passwords sheet, no prompt. The WebKit
heuristic `NsecLogin.tsx` relies on (credential fields leaving the DOM
plus a same-URL `pushState`, field-verified on v6.3.2) no longer fires.
A non-custodial app that lets a new user walk past the only copy of
their key has no last line of defence. Three changes, together.

**D1. Creation: one button, the manager does the saving.** Revised by
Jet 2026-10-04 (second pass). The generated key stays visible in its
mono block, rendered as the real visible password-type input with the
visible username input (npub) inside the existing `<form>` (see the D
addendum under I). One primary pill under it: **Save & continue**. It
is the form submit, so Bitwarden / Firefox / WebKit raise their own
save prompt on that tap; those prompts live in browser chrome, not on
the page, so the key stays visible while the user confirms it is real.
No checkbox, no second button, no separate Copy button on this screen.
The latest D1 revision supersedes the earlier same-tap-copy request: this
submit never writes to the clipboard. A pasted key never shows this block.

The app cannot see whether a manager saved anything, so Save &
continue sets no flag. The flag (`markRecoveryKeyBackedUp`) is set
only by an act the app can observe: a completed Copy or a
`credentials.store` Save on the Me row, or the user tapping
"It's saved" on that row. Until then D2's row stays amber and D3's
sign-out reminder shows the key. On the APK the Android Autofill
framework reaches the WebView (API 26+): whichever autofill service is
set (Google Password Manager, Bitwarden) offers the save on submit, as
the 6.4.19 code's "Android fired two prompts" note already proved. If
the Pixel does not offer, the form is wrong, not the platform.

Save & continue does nothing but submit. No clipboard write: a secret
placed on the clipboard without an explicit Copy is readable by any
desktop app and kept in plaintext by clipboard-history tools. Copy
stays explicit, on the Me row only.

Button family: signup, sign-in and sign-out use the same rounded pill
as the funding/claim cards. Sign out keeps its red outline; shape says
"button", colour says "destructive".

**D2. Me: the key lives under Wallet; the reminder lives at the top
only while it is needed.** Revised by Jet 2026-10-04 after seeing the
saved card sit at the top of Me ("looks misplaced"). Two placements,
one component:

- *Unsaved:* an amber row directly under the identity card, "Recovery
  key — did your password manager save it?" with **It's saved** and
  **Show key** inline (Copy / Save inside). Attention glow, same family
  as the chama bar's needs-you state; no modal, no nag.
- *Saved:* nothing at the top of Me. The key is a plain row inside
  Me › Wallet, "Recovery key — Saved ✓ ›", tap to reveal with Copy and
  Save. Same row is where "Show key" lands from the amber state.

The flag (`markRecoveryKeyBackedUp`) is set only by It's saved, a
completed Copy, or a `credentials.store` Save. It survives reload and
is scoped to the pubkey. The old Me › Advanced master-key reveal goes
away; Wallet is its one home.

**D3. Sign out: see you soon, not goodbye.** Revised by Jet
2026-10-04. Signing out is usually "back in a second with another
identity", so the dialog is light. If the flag is set: title "Sign out
of Chama?", one line "Your key stays in your password manager. Sign
back in any time.", pills **Sign out** (red outline) and **Cancel**;
no key line, no "Saved ✓", nothing to reassure. If the flag is unset:
the same dialog with the key block, Copy and Save inline, and the
primary reads **I saved it — sign out**. Never block a user who
insists. Sign-in and sign-out share the pill shape on purpose: the
same door both ways.

Copy for D1–D3 in four languages. Tests: Save & continue leaves the backup flag unset; completed Copy/Save or
“It’s saved” on Me sets it; pasted key is unaffected; the
flag survives reload; sign-out dialog shows the key block only when

## H. Who holds the money: name the federation on every circle

A circle is bound to one federation (`mintUrl`, `fed`, `fedPrefix` on
the CREATE; `policy.ts` enforces it across rounds and shares;
`escrow-bridge.ts` refuses cross-federation notes before LOCK). The
mechanics are safe. What is missing is the disclosure: every share is
ecash, an IOU from that federation's guardians, held for the whole
cycle, and the host chose the federation. A host running a one-box
"federation" can create a valid circle in which every member's sats
are, in practice, held by the host. Nothing in the UI says so today.

Custom invites exist (`setCustomFederationInvite`, any `fed1…`), so
"only curated federations" is not enforced by construction; it is
enforced only by the member having to connect to the circle's
federation before funding (`circle.fundingUnavailable`). That moment
is where the warning belongs.

- **Card and Lock confirmation, always:** one line, "Held by
  <federation name> · n guardians", from the invite's config. Name
  from `federationNameForInvite` for curated presets, else the
  federation's own `federation_name` meta, else the short id. A quiet
  "your federation" mark when it matches the member's current wallet
  (`trade.sameFederation` exists).
- **Earned warning 1 — not on Chama's list:** `mintUrl` is not in
  `CURATED_PRESETS` and not the member's community federation.
  "You'd be trusting guardians Chama hasn't vetted for the length of
  this circle (until <roundEnd>)." Shown before the seat hold, again on
  Lock.
- **Earned warning 2 — looks like one operator:** fewer than 4
  guardians, or all guardian API endpoints share one hostname / one
  IP literal / one registrable domain (compare hostnames from the
  invite's config; no DNS in a browser, so hostname-level only), or
  the host's pubkey appears in the guardian set. "This federation
  looks like it runs on one machine. If it goes away, so do the
  shares." Stronger colour; still not a block.
- The `fed` tag is already public on the CREATE; surfacing it leaks
  nothing new. No protocol change, no new events.

Test: curated federation → line only; custom invite → warning 1;
3-guardian or single-host config → warning 2; both → both. Four
languages.

## I. Start small: a share cap for public circles (decision needed)

Public circles carry the ROSCA default risk (collect round 1, skip
round 2) and the federation risk (guardians abandon or collude) in
proportion to share × members × duration. Slicing does the same job
for trades. Proposal: a per-share cap that applies to any circle
listed publicly (`unlisted` false), host-set up to an app maximum;
"just us" circles uncapped but the create form defaults to the same
small number with a "start small" line. The engine already fixes
`shareMsats` for a whole cycle (`policy.ts`: "Rotation rounds must
keep the cycle terms"), so the cap is per cycle, not per round; a
re-formed next cycle of the same group may go higher. That is the
graduation path: prove the group at a small size, then raise it.

Numbers (Jet, 2026-10-04): public default **1,000 sats**, private
default **1,000 sats** (small enough to clear any Lightning route).
Public maximum is derived from the federation, not hand-picked: the
share must fit one invoice and the collector's payout must fit the
federation's balance ceiling, so
`maxShare = min(fedi:max_invoice_msats, floor(fedi:max_balance_msats / seats))`,
read from the federation meta (`getMetaConsensusValue`; both keys are
present on the Fedi federation per the Safari console). Falls back to
the invoice ceiling alone when a federation has no balance key. The
create form shows the derived max next to the field and refuses above
it for public circles; "just us" circles see it as advice. The Row 5
test run uses the public default. Four languages for the form copy and
the Browse card line ("1,000 sats each · public · max 50,000").

A cycle is one full rotation (every member collects once): members ×
round length, each round ≤ the two-week hold bound in `circle.ts`.

### D, addendum — why no password manager ever offered (found 2026-10-04)

Firefox and Zen have no `PasswordCredential`, so the Chromium save path
never existed on Jet's desktop; Firefox's own save offer is off; the
only candidate was Bitwarden. In 6.4.19 the generated-key credential
pair was rendered hidden (`HIDDEN_CREDENTIAL_STYLE`), `readOnly`,
programmatically filled, and unmounted on submit. Every manager
(Bitwarden, Firefox, WebKit) ignores invisible, untouched fields by
design, as an anti-phishing rule. Same cause on iOS Safari. One build
to try: the visible key block becomes a real visible password-type
input with a visible username input (npub) inside the existing
`<form>`, submit event fires before unmount; test in Firefox +
Bitwarden on localhost against `https://fill.dev/form/login-simple`
as the control. If managers still do not offer, drop the apparatus
for good and keep Copy as the one act (D1 already assumes this).

## J. Two doors, never on the same screen

Rejected by Jet 2026-10-04: the build that put Create my account, the
paste field, Open the door, "Sign in another way" and the keep-me box
on one page. The mistake is structural, not cosmetic: the sign-in page
reuses one component for two different people. Build it as a chooser
and two separate flows.

**Screen 0 — the chooser.** Logo, community card, the two lines of
copy, then two pills of the same shape: **Become a citizen** (primary
fill) and **I'm a citizen** (outline). Jet 2026-10-04, fourth pass:
the middle ground between "Create my account / Sign in" (clear to
anyone, says nothing) and a single word (says everything, clear to
nobody). Same word on both pills, so which is which is obvious, and
the word is *citizen*, the hook for the window-shopper. Where the
language genders it (es, fr) the returning pill says "I'm from here"
— "Ya soy de aquí", "Je suis d'ici" — and the joining pill is the
plain verb — "Únete", "Rejoindre Chama"; Swahili has no gender, so
"Kuwa mwananchi / Mimi ni mwananchi" (*mwananchi*: child of the
land). The first line inside the joining flow makes the promise:
"Your citizenship starts here." No "account": a first-timer gets a
key, not an account. Background stays clean; no art behind the
chooser. Below the pills, the bare `LanguagePills` row (endonyms, as
on the country picker), because the chooser and the two flows are the
one place a wrong language loses someone; the language still
auto-detects from `navigator.language` on first run and persists, so
most people never touch it. The picker stays on the country picker
and in Me as well. Nothing else on the chooser: no field, no checkbox,
no links. Lane 1 (a stored key) never shows this screen at
all; it goes straight to Browse, as today.

**Express lane (Jet's meaning): no federation or country step.** A
first-timer never picks a federation or a community on the way in.
The community card already on the chooser ("USA · USD · last Chama
used in this browser · Change") is the whole of it: default from the
last community used in this browser, else from locale; the federation
is that community's pinned one (`resolveFederationForCommunity`), else
BLF. Become a citizen goes pill → key screen → Save & continue →
Browse, with those defaults applied silently; the country picker and
the federation list stay reachable later from the Change chip and
Me › Community. Nobody who knows what they want has to queue, and
nobody who doesn't has to decide. A stored key skips the chooser
entirely, which is why a signed-in browser never shows it.

**Choosing.** Tapping one pill fades the other out (opacity + a short
height collapse, ~250 ms; reduced motion: instant) and the chosen flow
grows in below the logo. A ‹ Back at the top of either flow returns to
the chooser. The two flows share nothing on screen; they are two
components with one parent that decides which is mounted.

**I'm a citizen (returning flow).** Heading "Welcome home, citizen."
then one line: "Paste the key you saved when you became
one." One field (`name="password"`,
`autocomplete="current-password"`, no npub field; managers fill a
password field on its own and Bitwarden already lists the saved
logins). A valid paste signs in on its own; Enter also submits; there
is **no button for the paste** (Jet, 2026-10-04: "a paste that works
needs no button"). A wrong or partial paste is one sentence under the
field and a short shake (reduced motion: no shake). Below the field,
the **Keep me signed in on this device** box, checked.

Then the named triggers, each its own outline pill, each doing one
thing on tap and nothing before it: **Sign in with browser extension**
(NIP-07; rendered only when `window.nostr` exists; one
`getPublicKey` request on tap) and, when it ships, **Sign in with
remote signer** (NIP-46). No automatic extension sign-in anywhere. No
"Sign in another way" grouping while there is at most one alternative;
add the group label only when there are two. A refusal or missing
permission is one plain sentence under the pill, never the raw string
("Your signer didn't approve Chama. Allow it in the extension, or
paste your recovery key."); known strings (nos2x "Insufficient
permissions", Alby "User rejected", timeouts) map to it; raw text to
console.

**Become a citizen (new flow).** Heading "Your citizenship starts
here." Then the generated key block as the real
visible password-type input, the small muted npub line ("your public
name") the manager needs to file the login, **Save & continue** as the
single pill (D1), the keep-me box. Nothing about pasting, nothing
about extensions.

Teaching happens in place later (small ? bubbles where a choice is
made), not on either screen. Copy in four languages. Tests: the
chooser renders no input; choosing mounts exactly one flow and
unmounts the other; Back restores the chooser; NIP-07 refusal renders
the sentence and never the raw message; valid paste signs in without a
tap and renders no button; the extension pill is absent when no
extension is present and makes no request until tapped.

## K. One sign-in, one popup

Report from a friend: depending on the extension, several permission
popups appear on sign-in. Reading `signers.ts` and `seed-manager.ts`,
that is what the app does today with an extension: `getPublicKey`
(popup 1), then the Fedimint seed is looked up on relays and
`nip44Decrypt` is tried on each candidate seed event in a loop
(`seed-manager.ts` ~L161; one popup per candidate on nos2x unless the
user chose "always"), then a seed event may be signed and published
(another), then every encrypted trade envelope and chat line is a
decrypt of its own. Extensions that remember per-method permission
(Alby "always", nos2x per-level) go quiet after the first round;
others ask every time.

Rules:

- Sign-in asks the extension for exactly one thing: the public key.
  Nothing else is signed or decrypted until the user does something
  that needs it.
- Seed lookup decrypts the newest candidate first and stops on success;
  the loop over every candidate is the bug. The seed step itself is
  deferred to the first wallet use, not sign-in.
- Decrypts for trade envelopes are batched behind one user action
  ("Open trade") and cached (`cachePromise` exists); never on list
  render.
- First time an extension is used: one line under the Welcome back
  pill, "Your extension may ask once per action. Choose 'always allow'
  for Chama to stop the prompts," with the extension name when known.
- Every extension prompt the user rejects, on any action, gets one
  sentence naming the action and its consequence, plus a retry: "Your
  signer didn't approve sending this message. Nothing was sent." /
  "Your signer didn't approve opening this trade. Try again, or sign
  in with your recovery key." Raw extension text to the console only.
  The extension decides how often it prompts; Chama decides that each
  user action makes exactly one request and that nothing is requested
  in the background.
- Test: sign-in with a NIP-07 stub counts calls; exactly one before
  the first user action; a rejected signEvent renders the sentence and
  publishes nothing.

## N. Liveness reads 0 for a newcomer (evidence first)
