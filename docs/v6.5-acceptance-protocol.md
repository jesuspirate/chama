# v6.5 acceptance protocol — how to give each row a thumb

Written against v6.4.7 (`dd0f843d`). Every step here ends in PASS or FAIL,
recorded in `docs/v6.5-readiness.md` with the date and the device. A step
you skipped is a FAIL, not a blank.

Read this first: **one of the four rows is not testable today.** Row 4 needs
something that does not exist yet. Details in its section — do not spend an
evening trying to measure it.

---

## Pass 0 — does 6.4.7 itself hold up (single device, ~20 min)

Everything here is new in 6.4.7 and none of it has met a human yet.

### 0.1 Automated, in one go

```sh
npm test                       # expect: Results: 4198 passed, 0 failed
npm run typecheck
npm run build
npm run repo:hygiene
```

Then, with a dev server running (`npm run dev` in another shell):

```sh
node scripts/verify-payment-card.mjs
node scripts/verify-wordmark-dot.mjs
node scripts/check-landing-deploy.mjs
```

PASS = all green. Any failure stops the protocol here.

### 0.2 The false-claim guard — the thing 6.4.7 exists for

The point is that Chama refuses to promise money it cannot prove. You need a
trade whose history will NOT replay on this device.

1. Open a trade you know is complete on another device but not here —
   `sm_mtnxzb5y_zpepqcpj` is the known one, and it is safe: it never locked.
2. Expect: a line saying the history could not be rebuilt on this device and
   that what you see is the saved summary.
3. Expect: **no** outcome sentence ("refunded to…", "ready to claim") and
   **no** Claim button.
4. FAIL if any amount is presented as claimable, or any outcome is stated.

Then confirm the diagnostic agrees:

```sh
npx tsx scripts/inspect-trade-relays.ts sm_mtnxzb5y_zpepqcpj
```

Expect pass 3 to print `CREATE → CREATED, JOIN → CREATED, CANCEL → EXPIRED`
and no LOCK. If the screen and the replay disagree, the screen is wrong —
that is the whole lesson of this release.

### 0.3 One alarm at a time

Needs a device carrying more than one money-safety item (a stranded note plus
a leftover, or a lock recovery plus a pending export). If you cannot produce
one naturally, use the fixture harness: `npx tsx scripts/v65-ui-review.ts`.

1. Exactly **one** card glows. Count them.
2. Everything else appears as a row in one quiet bordered list below it.
3. Tap each quiet row: it opens the same thing its own card used to open.
4. The secondary buttons survive — reabsorb, dismiss, withdraw.
5. FAIL if two cards glow, or if any item that used to be visible is now
   reachable only by scrolling somewhere else.

### 0.4 The payment card, all three rails

On a real trade (small amount), open funding.

1. Lightning selected first, three rails in the toggle, no chevrons.
2. Tap the amount → fiat quote appears; tap again → back to sats.
3. Switch to on-chain: expect the **send total** and a fee line broken out.
4. Switch to ecash: expect the paste input, not a QR to scan.
5. With a live Lightning invoice on screen, try switching rails: expect
   Switch disabled with an explanation, not a silent no-op.
6. Check the QR: four brand corners, no clipped edge, readable in light mode.

### 0.5 Chat evidence note

Disconnect from `relay.chama.community` (airplane-mode the machine briefly,
or point the build at other relays) and open a trade's chat.

1. Expect a quiet grey line telling you to keep your original.
2. Reconnect → the line disappears.
3. Check one non-English language; it must be translated, not English.

### 0.6 Country search

Type `us` in the country picker. Expect United States at the top. Repeat with
`uk` and `uae`.

### 0.7 Storage refusal (the one nobody will hit, which is why it needs a look)

In a private window with site data blocked, reach the funding screen and try
to fund.

1. Expect a message saying **nothing was created and nothing was spent**, in
   your language, with a remedy.
2. FAIL if it says the lock failed, or if the message is English in a
   non-English session.

## Row 3 — native push, two devices

You need two Android phones: one **with** Play services, one **without** (or
with an installed UnifiedPush distributor). Both running the 6.4.7 APK.

### Before touching a phone

1. Create the Firebase Android app for `app.chama.market`.
2. Put its `google-services.json` in `android/app/` and rebuild the APK.
3. Set `FCM_SERVICE_ACCOUNT_FILE` on the VPS.
4. Health check, per `scripts/vps-webpush-watcher/README.md`:

```sh
curl -s https://<host>/health        # expect JSON with ok:true
curl -s -X POST https://<host>/register -d 'garbage'   # expect 400, not 204
```

FAIL the row here if either check is wrong — a phone test on a broken
watcher tells you nothing.

### The test

5. On each phone: install, sign in, **opt in** to background alerts.
6. Settings names the transport. Phone A should say FCM; phone B should say
   its UnifiedPush distributor. FAIL if either says the wrong one.
7. **Close both apps completely.** Not backgrounded — closed.
8. From a third device (laptop), advance a real trade state involving each
   phone in turn.
9. Expect a wake within a couple of seconds saying only *"There may be new
   activity. Open Chama to check."* FAIL if the notification names an amount,
   a counterparty, or an outcome — the wake must stay opaque.
10. Open the app; the state is there and verified.
11. Turn the opt-in OFF on phone A, repeat step 8: no notification arrives.
    FAIL if one does.
12. Privacy audit on the VPS: inspect `registrations.json` and the journal.
    There must be no pubkey, escrow id, amount or event body anywhere. Only
    endpoints and opaque tags. FAIL on any of those appearing.

Record: both device models, both transports, the timestamps of the wakes, and
the result of step 12.

## Row 4 — reader fleet compatibility: NOT MEASURABLE TODAY

Stop before you start. **Chama events carry no client or version tag.**
`TAGS` in `src/escrow-engine/types.ts` has `d`, `p`, `e`, `t`, `mint`,
`share_idx`, `fee_pk` — nothing that says what wrote the event. So there is
no way to look at the relays and learn what versions are reading.

Your three options, in order of honesty:

1. **Add a client tag now, then wait.** One optional tag on published events,
   ignored by every existing reader. After a few weeks the relays answer the
   question directly and permanently. This is the real fix and it is small.
2. **Proxy measures.** Zapstore install counts, Start9 package stats, web
   analytics for `getchama.app`. These count downloads, not readers, and they
   cannot tell you whether an old client chokes on a host-seat event. Weaker,
   available today.
3. **Bound the blast radius instead of measuring it.** Keep first circles
   small and among people you can reach, and treat the flags as reversible.

Whichever you choose, write the choice and its reasoning into row 4. Do not
mark it PASS on option 2 alone.

## Row 5 — two-device full cycle with the host locking last

This is the one that needs the flags ON, which is the awkward part: turning
on `CHAMA_RING_WRITER_ENABLED` changes what gets **written** to relays.

**Sequencing matters.** Until row 4 is answered, do not let ring-writer events
reach the public relays where unknown readers will meet them. Run this cycle
against `relay.chama.community` alone, or a local relay, on a dev build with
both flags flipped locally. Do not ship the flags to test them.

1. Dev build, both flags `true` in
   `src/escrow-engine/experimental-escrow-features.ts`, relay list narrowed.
2. Two devices, two real identities, smallest amounts you are willing to lose.
3. Create a circle on device A. Join from device B.
4. Fill every seat **except the host's**. Host locks LAST.
5. Confirm device B's copy shows the same seat states as A at each step — not
   eventually, but after each action completes.
6. Run one collection round to completion.
7. Confirm on both devices: the payout landed, standing updated, and the
   chain replays cleanly on a third cold client (`inspect-trade-relays.ts`).
8. FAIL if any step needed a manual heal, a refresh to become correct, or
   produced a replay note that was not benign.

Record: both device models, the circle id, the amounts, the timestamps of each
lock, and the cold-replay output.

## The flip itself

Both flags change in the **same release**. Before it:

- Every row above is PASS, with evidence attached, or explicitly reasoned
  (row 4).
- Cycle-failure and sacrifice-round copy exists in en/es/fr/sw.
- First public circles stay small.

After it: keep `inspect-trade-relays.ts` handy and re-run the cold replay on
the first real circle within a day. The rollback is a patch release with both
flags back to `false` — readers stay intact, which is why they were built that
way.
