[trade](https://getchama.app/?trade=sm_mun8x4s2_4g6x53c8).

## 1. Bestie's JOIN: does it carry a `w` tag?

**No.** Both signed buyer JOINs lack it.

The current JOIN builder at `src/escrow-engine/escrow-client.ts:1731` puts
only the joiner's key in the `p` tag on this ecash path. The seller is in
committed state but is not included in the unsigned event passed to the
tagger. `makeChainEventTagger` at `src/notifications/watch-tags.ts:72`
looks exclusively at event `p` tags and removes the signer's own key.
It therefore finds zero peers and returns `[]` at line 75. The call through
`signWithSimTag` exists at client line 1761; it is the tagger's peer input
that is missing, rather than an absent tagger invocation in this source.

Replayed the real observed tag arrays through the real tagger with a dummy
conversation key and counting signer, without publishing. Both JOINs made
zero peer derivations and returned zero wake tags. This proves the peer
selection failure even when an ECDH-capable signer is available. It does
not independently prove what signer configuration the web device used.
Saved results in
[evidence/v6.4.14-brief-02-peer-selection.json](evidence/v6.4.14-brief-02-peer-selection.json).

## 2. Pixel pair watch, CREATE seeding and community watch

**Pixel registration is unknown.** The Java status API returns a
`registered` boolean, not the stored tag list
(`android/app/src/main/java/app/chama/market/ChamaPushPlugin.java:32`).
A green registration status alone cannot establish that a particular tag
is registered, or that registration was present at 18:27. No connected
Pixel, Android debugging tool or device export was available here.

The pair formula is `deriveWatchTag(conversationKey(me, peer), escrowId, 0)`
(`src/notifications/watch-tags.ts:82`). The first LOCK `w` tag,
`yVYmRjGuSahT7Lwg`, is the seller/buyer pair candidate: this is inferred
from its ordered `p` tags and the tagger's ordered peer traversal. The
second corresponds to the arbiter in that traversal. This is not an
independent ECDH derivation; neither identity's secret was accessed. A
Pixel tag export can be compared with the pair candidate, and a local
signer derivation can confirm it.

`openTradeWatchTags` considers actual committed participants, excluding
summary-only and terminal trades, and never uses community pool membership
as an obligation (`src/notifications/watch-tags.ts:105`). Running it on a
CREATED listing with only its creator seated returns zero tags. After the
buyer is known it derives one seller/buyer tag. Both cases were measured
with the real seeder helper and are in the peer-selection evidence file.
The hook seeds on launch, discovered state updates, enable and resume
(`src/hooks/useEscrow.ts:3017`). Thus foreground discovery can seed the
pair, but a phone already closed before the first JOIN has no way to know
which buyer's ECDH pair to register.

The listing's community is `us-blf`. Its public community wake tag,
computed with the actual helper, is **`pJrL9SDSgkIASUGA`**.
I cannot confirm that the Pixel holds it. More importantly, the current
code does not guarantee this registration on listing CREATE or launch:
the only caller of `registerCommunityWake` is the saved search-intent
handler at `src/ui/screens/AssistedCanvas.tsx:631`, line 640. The open-trade
seeder does not register community tags.

Even if that tag is already registered, the current watcher cannot use it
to wake this first JOIN: `scripts/vps-webpush-watcher/watcher.mjs:205`
explicitly restricts automatic community wakes to parent CREATE events.
JOIN carries no `community` tag in this trade either. The brief's intended
community bootstrap behavior is therefore not currently implemented.
These are source findings, not confirmation of the deployed watcher's
version or of the Pixel's saved preferences.

## 3. CHAT kind 38108: does the tagger run?

**Yes in the publish path; it receives no peers.**

`sendChat` constructs kind 38108 with only `d` and `t` tags at
`src/escrow-engine/escrow-client.ts:2581`, then calls `signWithSimTag` at
line 2591. That helper invokes `config.chainEventTagger` at line 857.
The hook supplies `makeChainEventTagger(signer)` when creating the client.
The tagger finds no `p` tags and returns `[]` even with a working signer.
The three actual relay CHATs confirm this missing-tag outcome. The local
peer-selection check produces zero derivations for each. The LOCK serves
as a positive comparison: its observed tag arrays produce two derivations,
and its actual relay event carries two wake tags.

The watcher subscribes to 38100–38199, so kind 38108 is inside its band.
This is not a missing-chat-kind subscription finding.

## 4. Pixel alert log: no wakes or “nothing new”?

**Pending the Pixel log.** The relay evidence alone cannot distinguish
transport failure, a disabled/blocked device, replay failure, stale snapshot,
or a successful job that found no new alert. The untagged JOIN/CHATs do not
request a pair wake from the watcher, but other wakes could still run a job.

Inspect the timestamped log around 18:27 and the later events. Read the
job text and per-post verdicts as well as the top-level verdict:
`ChamaWakeWorker.java:90` currently writes `nothing-new` both for an empty
notification list and for a non-empty one, with different job text
(`nothing new` versus `N alert(s) found`). A bare `nothing-new` label is
therefore not sufficient evidence that replay found zero alerts. No entries
would mean no logged receipt in that interval, not proof of a particular
transport fault. The log UI is under Wallet/Settings → background alerts →
Alert log (`src/ui/screens/MeScreen.tsx:2933`).

## Findings to address after reviewing this report

1. **Peer input for JOIN and CHAT:** derive outgoing wakes from the current
   trade's committed peers, including the seller on the first buyer JOIN.
   Do not rely only on event `p` tags and do not use community-pool members.
   Tests must exercise the actual `joinEscrow` and `sendChat` publish paths;
   the existing watch-tag tests pass because they supply peer tags directly.
2. **First-JOIN bootstrap:** register a route before any buyer is known and
   make a first JOIN trigger that route. The current community tag's
   registration and CREATE-only watcher behavior do not provide this.
   A community solution must filter replay notifications to the creator's
   actual listing; waking saved-search users for all JOINs is insufficient.
   This requires client registration and watcher routing to agree.
3. **Pixel-only diagnosis remains open:** obtain the stored and accepted
   registration tags, enabled/ready state and the alert log from the test.
   Confirm the community/pair route and distinguish absent wakes from a job
   or notification-posting failure before attributing a transport cause.

No B application or watcher code changed. Existing watch-tag tests passed
when rerun, and the report records the production-path gap they miss.
