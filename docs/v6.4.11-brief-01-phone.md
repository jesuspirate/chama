## A. A background wake becomes the real notification

Foreground notifications are right: detailed, and tapping one opens the
trade. A background wake says only "There may be new activity. Open Chama
to check." (`ChamaPushStore.wake`, `R.string.push_activity`). Jet: not
what users want. The privacy reason stands — the VPS knows nothing about
the trade — but the phone does. On a wake, before showing anything:

1. In the UnifiedPush/FCM service, run a short bounded job (WorkManager
   expedited, or the receiver's own window, ≤ 8 s): read the local trade
   cache, fetch this identity's trades from the relays, reduce, and ask
   `needsYouReasonFor` what changed since `lastWake`.
2. If it produces a reason, post **that** notification, with the same
   title/body the foreground path would use, deep-linking to that trade.
   Several reasons → one notification per trade, grouped.
3. If the job fails or times out → today's generic line, unchanged.
4. Nothing in the job signs, spends or opens a wallet. Read-only.

Tests: a wake with a cached APPROVED trade needing a signature posts "Sign
the payout to Bestie"; a wake with nothing new posts nothing (not the
generic line); a wake with the network down posts the generic line.

## B. Diagnose why no background wake arrived (report first)

Jet force-closed the app and got nothing. Before A lands, Codex checks
and reports, no code unless a bug is found:

- Android "Force stop" puts the app in the stopped state; the OS delivers
  no broadcasts to it — UnifiedPush included — until the user opens it
  again. That alone explains Jet's result. Settings should say so under
  Background alerts: "Swiping Chama away is fine. Force stop switches
  alerts off until you open Chama again." Add that line (all four
  languages).
- ntfy: "Instant delivery" (its foreground service) must be on and
  battery optimisation off for ntfy on GrapheneOS, or its connection
  sleeps. Say it in the same Settings text when the distributor is ntfy.
- Verify the registration actually reached the VPS: the endpoint host is
  `ntfy.sh` (trusted by default) and the watcher accepted it. Add a
  "Send a test alert" button under Background alerts that asks the VPS
  to wake this device now; result shown in Settings within 30 s or "No
  reply from the alert server". This is the test Jet couldn't run.

## C. The keyboard eats the chat

Trade view on Pixel 8: opening the keyboard hides the lower half (chat)
entirely; Jet's workaround was a floating keyboard. Manifest has no
`windowSoftInputMode`; add `adjustResize` on MainActivity, and in the
web layer size the trade view with `visualViewport` (not `100vh`), keep
the composer above the keyboard, scroll the last message into view on
focus. Test on the APK with the keyboard open: composer visible, last
message visible, header still reachable.

## D. Status bar icons in light mode

Light theme: the Android status bar (clock, wifi, battery) turns white on
a light background. Use the Capacitor StatusBar plugin: `Style.Light`
(dark icons) when the app theme is light, `Style.Dark` when dark, updated
on theme change and on resume. Same for the navigation bar.

## E. One trade clock, same on every device

Inside the guided trade view, show the one deadline that matters for the
current stage, identically for all parties, derived from what every
device can verify: the join hold (from the JOIN timestamp), the lock
window, the payment window after LOCK, the dispute window, and for
on-chain the confirmation wait and the refund height (block-based, with
an "≈ 3 days" reading). One line under the seats: "Bestie has 1h 27m to
pay" / "Locks after 1 confirmation" / "Refund possible from block N
(≈ 29 days)". Same source as the countdowns that already exist in the
lock stage; extend, don't add a second clock.
