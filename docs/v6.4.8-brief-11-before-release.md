# Brief 11 — last fixes before 6.4.8 ships

From Jet's 2026-09-24 test. Ecash funding during the gateway outage is
**verified working** (Bill Pay, 1,212 sats, locked, released, claimed as
ecash). These are the items he wants fixed before release. Verified against
`b1e195e1`.

## A. The vote prompts tell each side the wrong direction — every vertical

`LiveTradeSurface.tsx:456` gives the **first** voter the deed question plus
`lts.confirmReleases` — *"Confirm and the {amount} release to the
counterparty."* `:520` gives the **second** voter the receipt question plus
`lts.whereGo` — *"Where do the {amount} go?"*

Who votes first is `firstHappyPathVoter` (`decisions.ts:1856`): SELLER in
marketplace, BUYER everywhere else — the non-locker, the one who did the
deed. And who a RELEASE pays is `payoutRecipientFor`: SELLER in marketplace,
BUYER everywhere else — **the same person**. So the first voter always
releases the sats to **themselves**, and "release to the counterparty" is
wrong in every vertical, not just Bill Pay. The second voter is the locker,
and for them a release really does go to the other side — which is the
sentence they don't get.

Fix — the subs swap and name the person (nym, per E):

- First voter (deed-doer): deed question unchanged (*"Did you pay the
  bill?"*), sub *"Once {name} confirms, the {amount} come to you."*
- Second voter (locker): receipt question unchanged (*"Was the bill
  paid?"*), sub *"Confirm and the {amount} release to {name}."*

en/es/fr/sw. Derive "to you" vs "to {name}" from `payoutRecipientFor(state,
RELEASE)` compared with the viewer — never from the vertical name — so a new
vertical can't reintroduce this. Test all four verticals × both voters.

community right now"*, the modal opens on **Ecash**, and the saved Lightning
address block is hidden until Lightning is selectable. Failure of a Lightning
payout offers ecash on the same screen, never only Try again.

## E. Names differ between browsers — the kind-0 lookup is off by default

Jet: one browser shows Bestie / BitcoinSafariTz, the other shows Deft Fish /
Swift Cat for the same people. Cause: `kind0Enabled` comes from
`readKind0Toggle(pubkey)` (`App.tsx:962`), a per-device localStorage flag that
is **off unless the user turned it on**. With it off, every counterparty shows
as a generated pseudonym, even people who set a name — a name Chama publishes
precisely so it travels with the key.

Fix: names **on by default**, with the existing toggle as the opt-out. The
current key can't tell "never chose" from "chose off" (off removes it), so
move to a versioned, user-scoped key storing explicit `"1"`/`"0"`; absence
means on. Then confirm one name per pubkey everywhere: room strip, arbiter
sentence, attention cards, notifications, offers. And confirm the pseudonym
fallback is deterministic from the pubkey, so two devices that both lack a
name at least show the *same* pseudonym.

## F. Show how to pay, inside the trade

The locker's revealed payment details (`state.lock.handle`, NIP-44, parties
only) render **only** in the full TradeDetail (`TradeDetail.tsx:4546`). The
guided room — the default view — never shows them, so the person paying fiat
has to open "More options" to learn where to send it. Add a quiet,
collapsible **"How to pay {name}"** row to the room once LOCKED, visible to
seated participants only, reusing `handleDisplayForViewer` and the networks
list. Collapsed by default is fine; missing is not.

## G. Payment methods follow you across verticals — verify

Saved payment details are one list for the whole app
(`chama_saved_handles`, `saved-handles.ts:36`), so a handle saved in Exchange
is available in Bill Pay and Market. Confirm the guided flow's **method
choices** (e.g. Strike + $cashtag on "How will you pay the USD?") also carry
into the other verticals' questions as pre-selected, and say so in the note.
Also note that `chama_saved_handles` is a raw key, not user-scoped: two
identities on one device share it. Scope it without losing existing data.
