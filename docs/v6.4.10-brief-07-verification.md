# Brief 07 verification

## A — Winner chooses before signing

Opening either trade view now performs a read-only settlement check. Only the
winner's explicit address submission or “Send to my Chama key instead” action
can build and publish a proposal. Repeated preparation for the same destination
reuses that proposal; concurrent local preparation calls share one operation.
The other signer waits for a winner-authored transaction and signs that exact
transaction after the existing independent UTXO, destination, fee and maturity
checks. A passed UI check is bound to its transaction ID.

The choice selector ignores malformed and non-winner proposals. A valid
signature by the other required signer freezes the transaction; later winner
destinations cannot supersede it. This applies to both cooperative and arbiter
settlements. Current-state checks before publication/signing catch a choice
changed while an asynchronous check was running. Recovery of already broadcast
legacy settlements remains available.

The shared App funding/claim handlers and modal mounts reject on-chain trades.
Browser checks exercise guided and full views: no proposal on mount, waiting
counterparty, explicit winner choice, signing the received proposal without
preparing another, and no ecash funding/claim handler invocation. Pure tests
use real PSBTs/signatures for winner authorization, pre-signature changes,
post-signature freezing, malformed traffic and duplicates.

Validation: typecheck, settlement-choice tests, and the isolated browser test
passed. Browser money actions are mocked; no live transaction was submitted.
