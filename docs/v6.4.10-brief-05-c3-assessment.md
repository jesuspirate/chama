# Brief 05 C3 — Can the buyer publish an on-chain LOCK?

**Assessment: feasible, but do not enable it in this pass.** A LOCK is a signed
claim about the committed deposit, not a spend authorization. The frozen funding
terms already bind the address, keys, network, refund height and dispute delay;
`onchainLockError` rejects a LOCK that changes them. Each recipient still has to
recompute the address and independently verify the named confirmed outpoint and
safe refund window before displaying payment instructions.

The current reducer deliberately requires the category's funder to sign LOCK
(`state-machine.ts`, `handleLock`, `WRONG_LOCKER`), and `publishOnchainLock` calls
`client.lockEscrow` as that signer. To let the buyer publish, the reducer would
need an on-chain-only exception after valid committed terms, a seated buyer,
and a LOCK payload matching the frozen seats and amount. The client would need
a separate buyer action that recomputes and verifies the chain deposit before
calling `lockEscrow`; it must not reuse the funder's ecash path. Both clients
would need regression coverage for buyer-authored LOCK replay, duplicate LOCKs,
reorgs, spent/refunded deposits, underfunding, ranged amounts and an expiring
refund window.

**Main risk:** reducer replay cannot query Bitcoin. A malicious buyer could
sign a syntactically valid LOCK naming a nonexistent or later-spent output.
Until independent chain verification succeeds, the seller's device must show
only “checking deposit” and suppress any “pay now” instruction. A reorg or
refund can invalidate yesterday's check, so checks must continue after LOCK.
The buyer's LOCK also cannot end refund/voting rights by itself. The existing
funder-only rule remains in force until these gates and two-device tests land.
