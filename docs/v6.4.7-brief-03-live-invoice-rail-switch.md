# Brief 03 — the live-invoice rail switch (B2 departure)

`docs/v6.5-ui-implementation.md` records the departure honestly:

> The current wallet API has no invoice cancellation operation. Aborting
> `runFundAndLock` only stops the receive watcher; it does not invalidate an
> already issued BOLT11. … Instant live-invoice switching requires a backend
> cancellation guarantee and is not implemented in this pass.

That was the right call for that pass. This brief says what actually closes it.

Author: Claude. Verified against `bb3d4091`.

## Reframe the problem

Chasing invoice cancellation is the wrong target. Even with a cancellation API,
there is a race: the payer can pay in the window between our decision to cancel
and the federation acting on it. And regardless of the Switch button, a user can
abandon a funding flow today by closing the tab, backgrounding the app, or
losing connectivity — the invoice stays payable either way.

So the real requirement is not "make the invoice stop working". It is:

> **Sats that arrive on an invoice we stopped watching must still reach the
> user.**

That is a money-safety property Chama owes independently of this button. Build
it, and the Switch guard becomes a UI detail rather than a custody risk.

## Build, in this order

### 1. Make the receive watcher's abandonment recorded, not silent

When `runFundAndLock` is aborted (rail switch, navigation, teardown), do not
just stop the watcher. Record the abandoned invoice in a user-scoped store with
the same fail-closed discipline as the `pending-native-locks` stash: the entry
never ages out and is retired only by a positive outcome — paid-and-swept, or
expired-and-confirmed-unpaid by the wallet.

### 2. Reconcile on boot and on wallet connect

On startup and whenever the wallet reconnects, walk the abandoned-invoice store
and ask the wallet whether each one was paid. A paid abandoned invoice becomes
an ordinary balance the user can see and spend. An expired unpaid one is
retired silently.

Check what `src/fedimint/sdk-adapter.ts` exposes for querying a past receive
before designing this — if the SDK cannot answer "was this invoice paid", say
so in the implementation doc and stop at step 1, because steps 2–4 rest on it.
Do not invent an answer.

### 3. Only then, allow the switch

With reconciliation in place, switching rails while an invoice is live becomes
safe, and the copy becomes truthful: *"The Lightning invoice stays payable for
now. If someone pays it, the sats land in your wallet and you can use them for
this trade."* That sentence is only allowed to ship once step 2 is real. Until
then, the existing disabled-with-explanation state is the honest UI and stays.

### 4. Surface an abandoned invoice that got paid

A recovered payment must appear where the user looks — and per brief 01, it is
a money-safety entry, so it goes through `selectMoneySafetyFocus` rather than
adding a new banner. Coordinate with brief 01; if brief 01 has not landed yet,
add the entry type there rather than building a standalone card.

## Tests

- Abort mid-flight, assert an entry is written with the invoice identifier.
- Reconciliation with a paid invoice yields a spendable balance and retires the
  entry.
- Reconciliation with an expired unpaid invoice retires the entry quietly.
- The entry survives a reload (it is a money-bearing record; a 24h TTL or a cap
  that can drop it is a bug — same law as the preferred-relay queue).
- The Switch guard stays disabled when reconciliation is unavailable.

## What NOT to do

- Do not start a competing funding run while an invoice is live.
- Do not tell the user an invoice "stops working". We cannot make that true.
- Do not hard-fail a lock on an abandoned invoice. By then ecash may be spent;
  throwing strands it. Apply locally, mark custody unconfirmed, say so — the
  rule 6.4.6 already established for money publishes.

## Verification

`npm run typecheck`, `npm test`, `npm run build`, and
`node scripts/verify-payment-card.mjs` against a dev server — the existing
browser check already covers the live-invoice switch guard, so extend it rather
than writing a second harness.
