# Brief 05 — the storage-blocked funding error is untranslated and misframed

Small, and it should land before 6.4.7 ships. It does not reopen the
fail-closed decision; it fixes how that decision presents to a user.

Author: Claude. Verified against `b0a44299`.

## What a user actually sees today

`createFundingInvoiceJournal` throws four raw English strings
(`src/payments/abandoned-invoices.ts:27,29,40,47`). The journal is created
inside the `fundAndLock` action, which the funding modal awaits, and
`AtomicFundingModal.tsx:400-403` puts `(e as Error).message` straight into the
`lock-failed` phase.

So on a device with blocked or corrupt localStorage, a Swahili or French user
meets an untranslated English sentence — *"Cannot safely record the funding
invoice on this device"* — presented in the **lock-failed** surface, which
reads as *your lock failed*. Nothing was attempted. No invoice existed, no
ecash moved, nothing is at risk. The copy says the opposite of the truth, in
the wrong language, with no remedy.

The fail-closed behaviour is right and stays: refusing before an invoice exists
strands nothing, which is what distinguishes it from 6.4.6's "never hard-fail a
lock" rule. The presentation is what is wrong.

## Build

1. **Move the four messages into i18n**, `fund.*` keys, en/es/fr/sw. Throw a
   typed error carrying a key rather than a sentence, so the boundary decides
   the wording. Distinguish two causes: storage unavailable, and storage
   present but unreadable/unwritable.
2. **Give each one a remedy.** Storage unavailable: private browsing or site
   data blocked — open Chama in a normal window, or in the installed app.
   Unreadable: do not clear this site's data; it may hold a record of money.
   A refusal without a next step is a dead end.
3. **Do not present it as `lock-failed`.** Add a distinct pre-flight phase (or
   reuse an existing pre-invoice error surface) whose copy says plainly that
   funding has not started and nothing was spent. The retry/cancel affordance
   stays.
4. **Check the reachability claim while you are there.** The premise of this
   brief is that a user can reach the funding screen on a device with blocked
   localStorage — Codex's note says user-scope reads tolerate failure and nsec
   saving is optional, which implies yes. Confirm it. If the app in fact cannot
   reach funding at all without localStorage, say so, and this whole brief
   collapses to i18n hygiene.

## What NOT to do

- Do not degrade to "fund anyway without a record". An issued invoice we cannot
  record is exactly the untracked-money case the journal exists to prevent.
- Do not swallow the throw.

## Verification

`npm run typecheck`, `npm test` (i18n parity will catch a key added to three
languages and not four), `npm run repo:hygiene`. Then exercise the funding
modal with storage stubbed to throw, in one non-English locale, and read what
the screen says.
