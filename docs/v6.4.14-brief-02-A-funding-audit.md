# Brief 02 A — seat-bound funding and refusal recovery

2026-09-29. No release, push, deployment, or wallet reset.

The funding preflight now runs the LOCK reducer against the current local
trade state with inert share placeholders. It checks the finalized basket,
seats, locker, arbiter pool, amounts and mode before any invoice or ecash
spend. It repeats after asynchronous probes if the state changed, and the
bridge runs it again before spending. Listing/hold expiry is checked
explicitly: the reducer's post-listing-expiry result can be `ok` with an
EXPIRED state, which does not mean a LOCK committed.

Lightning requests use the earliest seat/listing deadline, including the
signed JOIN hold's existing grace, minus 60 seconds. They also reserve 45
seconds for creation. Both the browser SDK and native bridge receive the
shorter lifetime. Before displaying a real invoice or passing it to NWC,
the hook decodes its actual BOLT11 expiry and refuses an unreadable, already
expired or overlong invoice. The card displays the seat countdown; the
payable QR closes at the earlier invoice deadline. It distinguishes the
payment window closing early from the seat actually lapsing. At lapse it
shows the requested unpaid copy, with Wait for them to rejoin and Post it
again (opens the posting form).

Preparing either an on-chain escrow address or an ecash wallet peg-in
requires at least ten minutes of seat/listing window remaining. Preparation
rechecks after network work; this is a minimum, not a promise that a Bitcoin
confirmation will arrive within ten minutes.

Confirmed wallet credit followed by a refused LOCK produces a durable,
identity/federation-scoped `lock-recovery` row. The amount is the observed
new wallet credit, including any premium; the copy does not infer credit
from a gateway's funded status. A late `claimed` receive callback also
records recovery after the payable card expired. The funding card, trade
room and Wallet show where those sats are. The bar uses its existing
stranded priority, including amounts below the generic recovery threshold,
and opens Wallet. Acknowledgement requires viewing Wallet on the matching
federation with the credited amount present. A row with spent bearer notes
still uses the existing native/Fedi recovery stores; it is not described as
wallet credit. Raw reducer failure text is not displayed for a paid LOCK
failure.

## Other money/event seams

- **LOCK after listing expiry:** checked before an invoice/spend and again
  before LOCK. Positive notes-hash confirmation also catches a stale action
  resolving without committing a LOCK. Confirmed wallet credit gets the
  wallet recovery explanation; spent notes retain the native lock journal.
- **LOCK with a stale arbiter:** current seats and the pool are checked by
  the same reducer preflight. A mismatch after spending retains the native
  bearer-note recovery entry. Fedi's existing generate/stash/reabsorb path
  returns its notes to Fedi on a refused LOCK; it now also repeats preflight
  immediately before generating notes.
- **CLAIM after cancellation:** `handleCancel` accepts only CREATED;
  `handleClaim` accepts only APPROVED. A valid cancelled chain therefore
  cannot contain funded escrow notes to claim. Native immediate CLAIM is
  published before redeem; rejection stops redeem. Deferred delivered CLAIM
  checks APPROVED and the committed notes hash in `publishDeliveredClaim`;
  it never reconstructs or pays a second time. Existing delivery/payout
  journals remain the recovery authority for money already delivered.

## Cancellation and remaining limits

There is no active incoming-Lightning-receive cancellation API in either
wallet adapter or the installed Fedimint SDK. This change uses the supported
invoice-expiry cancellation instead; it does **not** invent a cancel call
or stop the receive watch (which would miss late credit). The native
Fedimint LN receive implementation allows 60 seconds of expiry clock skew;
the 60-second LOCK margin accounts for that receive cancellation delay.
The new tests verify requested expiry, actual wire expiry, card-flow expiry
and recovery, not an unsupported active cancel operation.

An already-funded incoming contract can finish minting after the seat
lapses; Lightning expiry cannot revoke a payment already in flight. That
race is handled by truthful wallet recovery, not by loosening consensus
holds. The trade room's recovery notice is device-local. With the app killed,
existing durable invoice/native-lock journals remain authoritative; the new
late-credit callback runs only while the receive watcher is alive. This is
not a claim that all off-device or crash races have been eliminated.

## Verification

`src/payments/seat-funding.tests.ts` covers six-minute hold expiry, shorter
gateway default, no invoice window remaining, actual overlong/expired/invalid
BOLT11 refusal, unfinalized basket, lapsed/cancelled trade preflight,
ten-minute on-chain gate, expiry while unpaid, late credit, paid LOCK
refusal copy, persistent recovery acknowledgement and bar priority.
The existing escrow suite also verifies browser SDK expiry forwarding and
replaces its former expectation that a paid failure display raw diagnostics.

Validation: `npm run typecheck`, `npm test`, and `npm run build`.
