## Changes

- **Stable address:** the funder publishes a signed JOIN containing `fundingTerms`. The existing panel's “Prepare deposit address” action waits for a relay acknowledgement before exposing any address. The descriptor freezes keys, height, network and address; it cannot be replaced. Replays derive the same address without reading a live tip. CREATE now binds the Bitcoin network (default mainnet). No compatibility bypass was added for old on-chain LOCK fixtures.
- **Participant provenance:** principal keys must match their CREATE/JOIN keys. The arbiter uses its own JOIN key or an embedded, signature-verified bond announcement for the assigned arbiter/community/network. The funder checks that bond is funded/active before preparation. Thereafter the signed key and recomputed bond descriptor remain authoritative; renewing or reclaiming the bond cannot invalidate an already-funded escrow. Automatic assignment is frozen at funding commitment. Stale keys are cleared when an uncommitted seat changes hands.
- **No expired funding seats:** once a deposit address exists, its seats and descriptor stay reachable. Cancel/replacement is refused because an external payment may already be in flight. The normal trade timeout is preserved separately for LOCK.
- **Recipient check:** every trade-room client independently rebuilds the committed address and checks transaction output script/value, confirmation depth and unspent status. LOCK's named outpoint must exist among the verified outputs. While this has not succeeded, both the guided and full trade rooms withhold its pay/vote copy and says “Checking the deposit on the blockchain…”. Checks repeat every 30 seconds; errors revoke the local verified state. The client also rejects an immediately refundable deposit: the committed deadline must preserve the 4,320-block refund term relative to the funding block, allowing up to 144 blocks for confirmation delay, and leave more than the 144-block dispute window before counterpayment. A passed refund deadline always refuses a secured-deposit indication. Existing settlement recovery remains reachable from this check screen.
- **Automatic arbiter:** dispute signing resolves the committed bond key through the commitment store's `keyIndex`, derives that bond account key, and compares it again before signing. A missing record or wrong seed/index fails closed. The test performs a full DISPUTE sign/finalize round trip and verifies its actual witness signatures.
- **Refund:** the funder can refund after the committed CLTV height, including a deposit made before LOCK. The transaction has one output to the funder's deterministic per-trade wallet, exact locktime and non-final sequence, an input/fee/destination checklist, and a verified funder signature. The UI exposes it only after reading a mature tip. The existing payout sweep moves those funds onward. Signed settlement journaling supports broadcast/COMPLETE recovery and preserves the payout recovery index. Refund is explicitly represented in the settlement payload and an advisory completion marker. That marker does **not** make the reducer terminal: a malicious funder could sign a future refund immediately and otherwise disable the counterparty’s voting/arbitration rights. Both rooms display a completed refund only after verifying the actual confirmed transaction and all its outspends; payout recovery remains available. The generic list status remains the protocol status until chain-aware presentation is expanded.
- **Witness selection:** finalization selects signatures by both leaf hash and signer; it no longer risks using the first signature from a different leaf for REFUND. Tests verify the actual COOP, DISPUTE and REFUND witnesses cryptographically.
- Declared `@scure/bip32`, `@scure/bip39`, `@scure/base` and `@noble/curves` as direct dependencies at their already-locked versions.

## Exact steps to finish the funded tests

From `/Users/Jetty/chama`:

```sh
cargo install mutinynet-cli
mutinynet-cli login
mutinynet-cli limits

# A named run preserves the existing default keys and gives this run a fresh timeout.
export MUTINYNET_ESCROW_RUN=jet-649
npx tsx scripts/mutinynet-escrow-harness.ts init
```

Complete the CLI's GitHub device login yourself. For each of the four addresses printed by `init`, request at least 100,000 test sats:

```sh
mutinynet-cli onchain <printed-coop-address> --sats 100000
mutinynet-cli onchain <printed-dispute-address> --sats 100000
mutinynet-cli onchain <printed-refund-address> --sats 100000
mutinynet-cli onchain <printed-attack-address> --sats 100000
npx tsx scripts/mutinynet-escrow-harness.ts status
```

If the faucet quota is lower, fund from another **Mutinynet** wallet or return after the quota resets. The script refuses an underfunded or unconfirmed case; it does not mark it skipped/passed.

After confirmation:

```sh
npx tsx scripts/mutinynet-escrow-harness.ts run coop
npx tsx scripts/mutinynet-escrow-harness.ts run attack

# Optional extra consensus check, before the printed refund height:
npx tsx scripts/mutinynet-escrow-harness.ts early-refund

# Once the printed CLTV height is reached:
npx tsx scripts/mutinynet-escrow-harness.ts run refund

# Once the dispute deposit has 144 confirmations (about 72 minutes at 30s/block):
npx tsx scripts/mutinynet-escrow-harness.ts run dispute
npx tsx scripts/mutinynet-escrow-harness.ts status
```

The harness shortens **only the test fixture's refund height** to initial tip + 20 blocks (roughly 10 minutes) in these test trees; the application still uses 4,320 blocks. The accelerated REFUND fixture exercises Bitcoin CLTV and the shipping refund builder/checklist; it deliberately does not satisfy the application’s month-long counterpayment-window policy. DISPUTE keeps the application's 144-block CSV delay. The attack case checks a real confirmed deposit at the malicious tree, requires the shipping reducer to reject its LOCK, then recovers the test coins with the attacker-owned keys. Fee estimates come from the live test chain. Exact transaction bytes are journaled before broadcast so a retry can use the same transaction.

Keep the ignored key file until all test outputs have been recovered.
