# Brief 05 — funding storage refusal

The refusal remains fail-closed. No bypass, storage deletion, recovery claim,
or live payment is introduced.

`FundingStorageError` carries a translation key and whether it arose in the
journal factory before invoice creation. Storage accessor/read/write exceptions,
invalid JSON/records, missing account/federation context and failed readback
are classified. The hook and modal boundary preserve that information.

Preflight refusals render **Funding has not started**, with the explicit
statement that no new invoice was created or sats spent on this attempt.
Blocked storage offers a normal window/installed-app remedy. Unreadable history
advises retaining the device/data and contacting support. Unwritable storage
points to space and permissions, without suggesting clearing money records.
Missing context asks the user to reconnect/check the amount. All copy is in
en/es/fr/sw; retry and cancel remain available.

A later journal write can fail after the wallet has issued an invoice. That
error also carries a localized remedy, but deliberately remains an in-flight
failure: it cannot claim that funding has not started. Updating the journal
observation still cannot throw past an already committed LOCK.

## Reachability

This is not reducible to dictionary hygiene. `App.tsx` calls `actions.connect()`
after both the optional saved-nsec write and its caught failure. Identity-pin
storage is advisory and caught; user scope itself is in memory. The native-lock
intent write before Lightning funding is best-effort and caught. The funding
modal has no global localStorage-availability gate. A browser can also lose
storage access after sign-in. Thus the factory refusal is a reachable boundary,
not a condition made impossible by the app's sign-in contract.

The browser fixture mounts the actual modal, selects Lightning, then makes the
real localStorage accessor throw (or provides corrupt journal JSON). It invokes
the actual journal factory. Both the hook's phase mapping and the modal's
rejected-action boundary are exercised, with zero invoice calls. This is not a
claim that every private-browser or Fedi runtime supports every upstream wallet
operation, nor a real-money/device integration test.
