# v6.4.8 implementation: briefs 03 → 07 → 06 → 04 → 05

Implemented against this application repository. No release, deployment, version bump, or StartOS packaging change is included. The five supplied brief files are preserved.

## 03 — stuck trades and funding errors

The guided room now reads effective seats on a one-second clock, matching the reducer's seat model. The full TradeDetail already used effective participants. A released joining seat can JOIN the same listing again; a missed seller funding window no longer leaves Fund & lock available. The seller can post again, and the joining buyer can rejoin or return to offers. Expired listings do not solicit another JOIN. These messages are translated into English, Spanish, French, and Swahili.

**Creator role:** the current CREATE reducer seats a guided Exchange creator as SELLER. The creator has no expiring JOIN hold; the buyer's reservation expires. A third-slot creator in the reported screenshot is therefore not explained by the current Exchange CREATE convention. The creator's seat cannot lapse under this convention. Reposting after a missed buyer creates a new listing ID and retires the old listing locally.

**Routing:** AssistedCanvas's Review action passes `selected.listing.id` directly to `onOpenTrade`, which calls `openEscrow(id, "guided")`. It does not consult latest-trade or the durable index. Reopening one existing listing correctly retains its ID. A browser regression opens two listings by the same seller and observes two IDs. The historical claim that a newly posted listing opened an older ID was not reproduced.

**Errors:** a shared `errorText` retains Error messages, string rejections, structured message/error/reason fields, or JSON. Invoice failure logs the original rejection once. The card shows a plain failure statement, the actual reason, and Try again. Storage refusals keep their existing separate preflight copy. Invoice rejection invalidates the health cache instead of marking the federation unreachable; a new attempt gets a fresh reachability probe. An injected string rejection survives the actual funding orchestrator in regression coverage.

**On-chain:** a wallet without the capability exposes no On-chain rail. Native fee errors no longer imply that an unavailable rail is merely waiting to load. Below the minimum, the checkout uses the same row component as the fundable checkout, with the trade and negative shortfall in red and a Use Lightning action. The minimum comes from wallet info, with `pegInFeeSats + 1` as fallback.

The comparison against the **trade amount**, rather than gross deposit, remains a deliberate product floor. The federation might technically accept a 100-sat net trade with a 1,000-sat fee; the product continues to refuse that disproportionate fee. No production minimum is hardcoded.

## 07 — visible and spendable balance

The Wallet tab starts with an ordinary balance row, including zero and sub-2,000-sat amounts. It uses the existing interactive sats/fiat display. The 2,000-sat alert threshold is unchanged.

`spendableBalanceMsats` subtracts all supplied lock and payout earmarks, clamps at zero, and returns zero for unknown/invalid amounts. The funding path reads pending-lock ownership without interpreting unreadable storage as an empty reservation list. Pending payouts remain earmarked independently of the age limit used for recovery alerts. Pending history hydration or a running payout also prevents balance spending.

A CREATED trade covered by spendable balance opens with Lock from your balance and an option to pay fresh. The action rereads wallet balance and earmarks, checks that the selected order amount still matches, and uses the existing funding-operation guard and lock action. It reports success only with a committed notes hash. It creates no receive invoice and no abandoned-invoice journal entry. The existing native **lock recovery journal remains mandatory** around the spend; removing it would reopen the crash-loss window.

Partial top-up is not included. A simulated 500-sat wallet can lock a new 100-sat trade, leaving 400 sats, without displaying or requesting a Lightning invoice.

## 06 — renewal by lane

Only connected, signed-in sessions renew. Exchange, Bill Pay, and Work use their lane policy without Store's bond or toggle requirement. Store retains both requirements. The existing retired-ID ledger, per-session guard, five-listing cap, duplicate cleanup, and age-out remain.

A missed buyer funding window records a pause beside the renewal-age records, scoped to the seller and listing identity. The live missed-window predicate also blocks renewal if persistence fails. Only a successful manual renewal clears the pause. Existing age-counter keys and counts are preserved. The seller sees the pause explanation on their offer and the presence-based renewal explanation on their live offer and publication screen.

## 04 — deposit progress

The Rust bridge records each deposit-stream state and adds `GET /onchain/deposit-status?operationId=…`, verifying the operation exists in the active wallet and using the existing bridge authentication middleware. The existing await-deposit endpoint remains unchanged. The state cache is in memory; after a bridge restart, awaiting the operation again repopulates it from the wallet stream.

The shared optional subscription contract is `waiting → seen → confirmed → claimed`, or `failed`, with deposited sats, outpoint, and error where available. Native polls every three seconds, stops on terminal state, unsubscribe, or wallet cleanup, and suppresses late callbacks. Status-read failures do not falsely report deposit failure. The simulator now uses that same contract.

No confirmation count is fabricated. The card translates the quiet progress line in all four languages and keeps its QR/copy geometry fixed. The estimated wait uses the federation's finality requirement and Bitcoin's nominal ten-minute block interval; it is not a guaranteed arrival time.

## 08 — balance insurance budget and room timer

Balance funding now requires the trade amount plus insurance in App, the funding modal, and the action's fresh spendable-balance check. Premium normalization happens before funding-method selection, with zero insurance in simulation/testnet. The offer names the total, trade amount, and insurance in all four languages. The lock still spends only the trade amount, leaving insurance in the wallet for settlement.

Regression checks cover insufficient trade-only balance, the exact trade-plus-premium threshold, an unchanged balance after refusal, the remaining premium after locking, modal copy/visibility, and zero premiums in simulation/testnet.

The trade-room clock runs only while a matching buyer/seller seat hold is counting down, through its lock grace period. It stops after the last hold deadline and does not start in locked trades or tranche-plan rooms.
