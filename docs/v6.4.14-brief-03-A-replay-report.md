# Two truths: replay report before the fix

Trade `sm_mun8x4s2_4g6x53c8`. The seven-event public relay export is
`evidence/v6.4.14-brief-03-public-replay.json`; the previous wake report records
relay coverage and signature verification at collection time.

The defect is reproducible without a device clock difference. `sortEventChain`
in `src/escrow-engine/event-parser.ts` globally sorts all JOINs before all LOCKs.
It therefore applies the 18:36:07 renewal before the 18:34:53 LOCK. The reducer
checks the *replacement* hold (expires 18:41:07), not the first hold (expires
18:32:01, grace ends 18:34:01). It also fails to require that the finalization
already existed at the LOCK's signed timestamp. This makes a future JOIN
retroactively authorize an earlier LOCK.

`node --import tsx src/escrow-engine/two-truths.tests.ts` passes against the
unmodified implementation: applying the LOCK after only events preceding it
returns `ORDER_NOT_FINALIZED`; sorting and replaying all seven produces LOCKED
with 170,000 msats. This commit intentionally records the defective baseline;
the fix must change that expectation to CREATED, the second buyer hold, and an
explicit retained rejection of the first LOCK.

CREATE and both JOIN payloads in the fixture are the exact public bodies.
LOCK and CHAT are encrypted on the relay. Their test bodies are representative,
structurally valid bodies; share ciphertext and notesHash are placeholders.
The test uses the observed IDs, tags, authors, predecessors and signed times,
but does not verify signatures against substituted content. It proves the
ordering/finalization defect, not the exact private LOCK body or wallet balance.
No Pixel database, alert log, device clock, bearer notes or registration export
was supplied. The reported Pixel screen is consistent with replay after the
renewal, but a captured Pixel execution trace is still unavailable.

The candidate local bypass is not present in the inspected path:
`EscrowClient.applyLocally` parses the signed event using `raw.created_at`, then
calls the same `applyEvent` as replay. The old normal LOCK publication path
publishes before local apply, so a refused local LOCK can already exist on a
relay; an ACK proves transport, not reducer acceptance. No double grace or
alternate hold calculation is required to reproduce this incident. A device
clock error is neither established nor needed.

Fix requirements: preserve signed-time seat history; prevent future holds and
finalizations from authorizing earlier locks; retain a positively refused LOCK
outside committed custody so the listing and renewal remain usable. Unrelated
money errors must stay strict. A rejected LOCK must contribute zero to escrow
amounts; its funding recovery is a separate wallet obligation, addressed in B.

## Fix

Replay now respects predecessors and orders available branches by signed time
(with deterministic same-second ties). The reducer additionally requires the
selected hold and order finalization to predate the LOCK. Replay retains only
an ecash `ORDER_NOT_FINALIZED` refusal with its predecessor present as a
`rejectedLocks` record; it never inserts that LOCK into `eventChain` or `lock`.
Other money errors stay strict. Local apply still parses the signed event and
calls the same reducer. The regression now checks CREATED + second hold,
retained exact rejected ID, zero escrow sats, refusal against the renewed state,
and identical results across relay arrival permutations.

The final recovery review further bounds quarantine to a known, expired hold
whose signed JOIN is the LOCK's predecessor. Missing JOINs or missing order
history remain strict replay failures, never positive refund evidence. A
regression removes both JOINs and verifies this fail-closed boundary.
