## A. "No gateways available" — the federation has no Lightning gateway right now

This is the reason last night's production attempts failed too; brief 03's
error fix is what finally surfaced it.

The path: `sdk-adapter.ts` ~1703 calls `updateGatewayCache()` then
`listGateways()`. With **zero** gateways it logs
`[chama] LN receive gateway selection found no gateways` and returns
`undefined`; the WASM client then refuses the invoice with *"No gateways
available"* (string inside `fedimint_client_wasm_bg.wasm`). With one or more
gateways but none trusted, Chama would have thrown its own long "wallet-
verifiable gateway" error instead. So the federation reported **no
registered Lightning gateway at all** — not an untrusted one, not a 100-sat
floor. Fedimint v1 gateways register with a TTL (`LightningGateway.ttl` in
the SDK types); a gateway that stops re-registering drops off the list.
BLF is still on v1 modules (runway 8), so this is not an lnv2 mismatch.

**Confirmed by Jet, 2026-09-24, outside Chama:** the Fedi app on Bitcoin
Life shows *"No lightning gateways found for this user"* for a 200-sat send.
A second Gbot-hosted federation (Orange Club Africa) doesn't error — its
sends spin forever and leave pending Lightning payments behind. So Chama's
reading was right, and the fault isn't ours.

This is operational first: every browser user on BLF — including
getchama.app 6.4.7 — cannot fund with Lightning until a gateway re-registers.

**Code, in this pass:**

1. **Pre-flight, not post-failure.** When the funding card opens, run the
   same `updateGatewayCache` + `listGateways` check. With zero gateways, the
   Lightning rail says *"Lightning isn't available in this community right
   now"* and the card opens on the next rail that works (ecash, and on-chain
   once B lands). Nobody should tap Fund to discover this.
2. Map the WASM string to that sentence (en/es/fr/sw); keep the raw text as
   the small detail line, as now.
3. Put the gateway count in the diagnostics a user can copy, so a report from
   the field says "0 gateways" without a console.
4. **Payouts are hit too.** Claiming to a Lightning address needs a gateway
   just as funding does. The existing pay path already refuses honestly
   (*"No trusted Lightning pay gateway… your claimed sats are still in your
   Chama wallet; payout can be retried"*). Confirm that's what a user sees
   today when claiming on BLF, and that the claim card also offers
   **Withdraw as ecash**, which doesn't need a gateway.

## B. On-chain in the browser — the SDK can do it; we never wired it

**Next release, not 6.4.8** (Jet, 2026-09-24). Kept here so the finding
stays with its evidence.

Jet: *"is there a technical reason?"* No. `@fedimint/core` (our pinned
canary) exposes `FedimintWallet.wallet: WalletService` with
`generateAddress(extraMeta)`, `subscribeDeposit(operation_id, …)`,
`sendOnchain(amountSat, address, extraMeta)` and `getWalletSummary()`.
`sdk-adapter.ts` never references `.wallet`; the web adapter simply has no
`onchain`, which is why `fedimint-client.ts:684` tells you to start the native
bridge.

(Separately, and not the same thing: the tranche/slicing work settles on
Bitcoin between parties — `bitcoinNetwork`, child keys — and is paused behind
`TRADE_SLICING_ENABLED`. It is not federation peg-in and does not help here.)

**Build the web `onchain` adapter:**

- `createDepositAddress(meta)` → `wallet.generateAddress(meta)`.
- `subscribeDeposit` → `wallet.subscribeDeposit`, mapped onto brief 04's
  contract (`waiting → seen → confirmed → claimed | failed`). Do not add a
  confirmation counter the SDK doesn't give.
- `awaitDeposit` → resolve on the claimed state of that same subscription.
- `getInfo()` → finality delay, peg-in fee and minimum from the federation's
  wallet-module config. If they cannot be read honestly, the rail stays off —
  never guess a fee.
- **Withdraw:** `sendOnchain` exists but there is no fee-quote call in this
  SDK. Chama never withdraws without showing the total first. If no honest
  quote exists on web, web supports on-chain **funding** only and payouts say
  *"On-chain payouts work in the Chama app."* Say which in the note.

Then the brief-03 checkout (Trade / On-chain minimum / Short, in red) applies
on web too. This also gives funders a working path while Lightning gateways
are down — on-chain in, ecash locked, same as native.

## C. Two clocks for one deadline

Seller's attention card: *"lock in 0:50"*. Buyer's room, same moment:
*"for the seller to lock 2m 50s"*. Exactly 2:00 apart —
`JOIN_HOLD_LOCK_GRACE_SECONDS = 2 * 60` (`types.ts:91`).
`soonestJoinHoldExpirySec` (`attention-triage.ts`) uses `hold.expiresAt`;
`preLockDeadline` uses `expiresAt + grace`. One deadline everywhere: the
attention card uses `preLockDeadline`.

## E — Stores renew on presence (Jet: go, 2026-09-24)

The store lane auto-renews on presence like Exchange, with the same ghost
pause. The bond stops being the price of auto-renew and becomes the price of
a longer run: bonded stores keep `BONDED_TENURE_SECONDS` and the store
toggle's longer cycle cap; unbonded stores renew on presence with the 7-day
Exchange cap and age-out. Keep `MERCHANT_BOND_FLOOR_SATS` and the arbiter
floor exactly as they are — they still gate what they gate. Update
`resolveRenewalPolicy` and `sessionAllowsAutoRenew` together, and the
listing-renewal header comment, which currently says the bond buys
auto-renew.
