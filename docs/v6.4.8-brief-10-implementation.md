# Brief 10 — funding rails stay reachable

The funding modal shows Lightning, on-chain, and ecash above the payment card before payment detection. Unsupported browser on-chain funding is disabled with an explanation. Insufficient balance and Lightning amount/route restrictions also show their reasons. On-chain minimum and fee checks retain the existing checkout.

Browser preflight refreshes the gateway cache before listing gateways; native preflight uses the authenticated `/gateways` endpoint, which refreshes by default. Zero registered gateways prevents an invoice request and opens ecash, with the existing balance offer taking priority when it covers trade plus insurance. Unknown/failed checks are not called zero; an eight-second preflight timeout leaves the existing invoice checks responsible for an honest failure. Simulation and Fedi-internal funding keep their existing paths.

An invoice-creation failure shows the plain failure line and raw reason, opens the ecash chooser, and leaves supported on-chain funding reachable. Lightning remains disabled until an explicit secondary retry. That retry is unavailable once another receive has started. The live-invoice switch guard still refuses a competing run until expiry. Address-issued on-chain flows retain their existing no-switch guard. After payment detection, controls become unavailable while their space is retained so the QR does not jump.

This supersedes brief 05's rails-below-QR layout. It implements the gateway preflight needed from brief 09 A; the other brief 09 findings are outside this change, including the explicitly deferred browser on-chain adapter.
