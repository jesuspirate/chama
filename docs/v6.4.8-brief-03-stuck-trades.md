# Brief 03 — HOTFIX: two people could not trade (production, v6.4.7)

Found by Jet on 2026-09-23 on `getchama.app?sim=0` with two real identities
(Jetty, Bestie). Real money path. Nothing was lost — no lock ever happened —
but both people ended fully stuck. This outranks everything else in 6.4.8.

Author: Claude. Verified against `2d613b3b`.

## A. A lapsed seat is a dead end (VERIFIED root cause)

What Jet saw after the seller's lock window ran out:

- **Seller's screen:** "Lock 100 sats to start this trade?" with a live
  **Fund & lock** button — and directly under it, "Your seat was released —
  this listing is back in Browse." A lock button under a sentence saying the
  seat is gone.
- **Buyer's screen:** "The seller didn't lock in time, so the seats were
  released and this listing went back to Browse." No button. Refresh changes
  nothing. Tapping the listing in Browse lands on the same screen.

Both come from one line. `LiveTradeSurface.tsx:113`:

```ts
const participants = state.participants;
const myRole = samePubkey(participants[Role.BUYER], pubkey) ? Role.BUYER : …
```

`myRole` reads the **raw** participant map. But seat lapse is a clock fact:
the reducer only replaces a lapsed occupant when a new JOIN arrives
(`handleJoin` correctly uses `getEffectiveParticipantAt(state, role,
event.timestamp)`), and the UI's own `preLockDeadline` correctly computes
`lapsed` from the clock. The surface mixes the two:

- The lapsed **funder** still has `iAmFunder === true`, so the Decision
  renders Fund & lock, and `preLock.lapsed` adds the seat-released hint
  underneath (`LiveTradeSurface.tsx:253-262`).
- The lapsed **joiner** still has `myRole === BUYER`, so it takes the
  `myRole != null` branch → `lts.lockMissed` → `<Waiting>` with no action
  (`:268-277`). The unseated "Agree & join" branch, which is exactly what they
  need, is unreachable because `myRole` is not null.

**Fix.** On a CREATED trade, derive the viewer's seat from effective
participants at `now` (`getEffectiveParticipantsAt(state, nowSec)`), the same
source the reducer uses. A viewer whose hold lapsed is an unseated viewer and
gets **Agree & join** again — a fresh JOIN the reducer already accepts.

Check `TradeDetail.tsx:508` too: it computes `myRole` from raw participants
the same way. Any other `myRole` derivation on a CREATED trade gets the same
treatment. Grep for `samePubkey(participants` across `src/ui`.

**While there, confirm the seat model.** In the screenshots the room strip
reads `open seat · open seat · Quick Dikdik` after the lapse — both principal
seats empty and the listing's creator in the third slot. State plainly (in
the implementation note) which role the creator of a guided Exchange offer
holds, and whether the creator's own seat can lapse. If the creator is the
funder and their seat lapsed, the listing is dead and must not stay in Browse
looking alive.

**Tests.** A lapsed funder sees no lock button. A lapsed joiner sees Agree &
join. A live hold still sees its normal view. Assert on the decision helper,
not the DOM, where possible.

## C. "Couldn't create funding invoice" — the real error is thrown away

Third attempt, real funding: the modal said **"Couldn't lock the trade ·
Couldn't create funding invoice"**.

That sentence is a fallback. `fund-and-lock.ts:704`:

```ts
const err = e?.message || "Couldn't create funding invoice";
```

It only appears when the rejection has **no `.message`** — a string, a plain
object, or `undefined`. The wallet SDK path rethrows whatever it received
(`useEscrow.ts` ~4492: `throw e`), and SDK/worker errors commonly arrive as
strings. So the actual reason — gateway minimum, federation refusal, a busy
wallet, anything — was in our hands and discarded. `useEscrow` does compute
`String(e)` and stores it in `fedimint.error`, but the funding modal never
shows that, and nothing logs it.

**Fix, in order:**

1. One helper, `errorText(e: unknown): string` — `Error.message`, else a
   string as-is, else `.error` / `.reason` if present, else `JSON.stringify`,
   else the fallback. Use it at `fund-and-lock.ts:704` and anywhere else in
   the money path that does `e?.message ||`.
2. `console.error` the raw rejection object at that catch, once, so the next
   failure can be diagnosed from a browser console.
3. **Then** reproduce: 100-sat trade, Lightning, `?sim=0`, and record the real
   message in the implementation note. Do not guess the cause before the
   message exists. If it turns out to be an amount floor (a gateway minimum,
   or the premium making the invoice unpayable), the fix is a named,
   translated refusal **before** the invoice is requested, the same pattern as
   brief 05's storage refusal.

Note the side effect while you trace: a failed `createInvoice` marks the
wallet unhealthy (`healthRef = { ok: false }`), which can gate the next
attempt with "federation unreachable". Confirm a single invoice failure does
not poison the following tries for reasons unrelated to reachability.

## E. On-chain: an honest rail, and a checkout instead of a sentence

Two separate problems hid behind one line.

**1. On the web, on-chain can never work, and the card pretends it might.**
Jet's screenshot, *"Onchain unavailable until federation fees load"*, is the
`onchainInfoState.kind === "error"` branch (`AtomicFundingModal.tsx:782`).
The fees did not fail to load; they cannot load. The browser wallet adapter
has no `onchain` at all — `fedimint-client.ts:684` throws *"On-chain Fedimint
wallet support is not available in this wallet adapter. Start Chama with
nativeFedimint=1 and the Rust bridge."* So on getchama.app the On-chain rail
is a permanently dead button with a message implying it will come alive.

Fix: when the wallet has no `onchain`, do not show the On-chain rail on the
funding card. If Jet prefers it visible, it says *"On-chain works in the
Chama app"* — never "until fees load". Keep "checking fees" only for the real
loading state on native.

**2. Below the minimum, show the checkout, not a sentence.** On native, when
the trade is under the federation minimum, the card currently prints
`Minimum 1,001 sats. Use LN for this trade.` Replace it with the same
right-aligned checkout rows the funding card already uses for a fundable
on-chain amount (`fund.onchainTotalBreakdown`: trade + federation fee =
total), in the same position and type:

```
Trade                 100
On-chain minimum    1,001
─────────────────────────
Short                −901     ← red
```

The trade amount and the short line are red; the minimum is muted. Under it,
the one action: **Use Lightning**, which switches the rail. No sentence.

Every number comes from `getInfo()` — `minimumDepositSats`, falling back to
`pegInFeeSats + 1` exactly as the gate already does. Never a hardcoded 1,000
or 1,001. The rows must be the same component as the fundable checkout, so
the two states read as one screen with one thing wrong.

Note for the implementation record: the gate compares the **trade amount**
against `minimumDepositSats`, while the federation's minimum is on the
**gross deposit** (trade + fee). By the federation's own rule a 100-sat trade
is fundable on-chain for 1,100 sats sent — at a fee ten times the trade. The
current gate is therefore a product floor, not a protocol one. That is a
reasonable floor; write it down as a choice so nobody later "fixes" it into
letting people pay 1,000 sats to move 100.
