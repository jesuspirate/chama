# Chama v6.5 — the build brief

Written 2026-09-20, after v6.4.5 shipped. This is the single hand-off
document for the 6.5 cycle: one brief per item, ordered, each self-contained
and each with acceptance criteria that can be checked without asking the
author what they meant. The source discussion for every item lives in
`docs/v6.4-runway.md` under the numbers cited.

**The grand finale of 6.5 is the merry-go-round.** Everything else here is
either a precondition for flipping those flags with a straight face, or a
debt that will get louder once real money rotates through circles weekly.

## House rules for this cycle

1. **Pure first.** Decisions live in pure, tested functions; components read
   them. Every brief below names the pure unit it wants.
2. **Never claim what is not proven.** Copy that asserts a location, an
   outcome, or a recovery must be backed by evidence in hand — the honest
   alternative is naming what is NOT established.
3. **Four languages, always.** en/es/fr/sw in `src/i18n/<lang>/<domain>.ts`.
   A string in one file and not the others is a bug.
4. **Money paths stay strict.** LOCK and CLAIM transitions, bond checks and
   settlement classification do not get "friendlier" in this cycle.
5. **Tests are the deliverable, not the evidence of one.** `npm test` green,
   `tsc --noEmit` clean, and new assertions that would FAIL against today's
   code.

# BRIEF 1 — The replay that gives up too easily (runway 32) — BLOCKER

**Status: the sharpest open bug in the codebase. Do this first.**

## What is known

A real settled trade, `sm_mtnxzb5y_zpepqcpj` (₿2,000, market listing, seller
Jetty, buyer Bestie, outcome REFUND to the buyer):

- The seller tapped HEAL THIS TRADE and got "Re-published 6/6 events to
  today's relays".
- The buyer, same minute, pasted the ID into Load-a-trade and got
  **"This trade's history couldn't be rebuilt on this device… (INVALID_STATE)"**.

So delivery works. The relays have the events. The buyer's client cannot
REPLAY them: some event is applied to a state that does not accept it
(`src/escrow-engine/state-machine.ts` — "Cannot JOIN/LOCK/VOTE/RESOLVE/CLAIM
in state X"). The buyer is the winner of ₿2,000 and cannot claim.

## Work

**1a. Name the offending event.** `LoadFailure` already carries `eventId`; no
surface shows it. Include it (and the code) wherever a chain-incomplete
failure is reported — the Load-a-trade toast, the archived-trade toast, the
claim modal's incomplete-chain card. One read should identify the exact
transition that failed, not start a hunt.

**1b. Diagnose this trade specifically.** With 1a in place, determine which
event and which state. Write the finding into runway 32 before changing any
law — including the possibility that the chain really is invalid and the
right answer is a repair tool, not a looser replay.

**1c. The law to get right.** A replay that abandons an entire history
because ONE late or duplicate event does not fit is fragile by construction.
Duplicates are expected in a relay world — `useEscrow` already says so
("deduped at replay via ALREADY_VOTED / TERMINAL_STATE / INVALID_STATE").
Proposal to evaluate, not to assume:

- A **non-money-bearing** event that cannot apply (a duplicate VOTE, a second
  RESOLVE, a JOIN after the seat filled) is SKIPPED, recorded in a replay
  note, and the rebuild continues.
- A **money-bearing** transition (LOCK, CLAIM, and anything that moves or
  assigns funds) stays strict: if it cannot apply, the rebuild fails as it
  does today.
- The resulting state must carry the skip list, so a UI can say "rebuilt,
  ignoring 1 duplicate vote" rather than pretending the chain was clean.

**1d. Auto-heal on open.** When a client opens a trade and holds signed
events the relays did not return, publish them without being asked. A winner
must never depend on the counterparty finding a button behind a gear icon.

## Acceptance

- A test that replays a chain with a duplicate VOTE and a second RESOLVE and
  rebuilds successfully, with the skips recorded.
- A test that a LOCK or CLAIM which cannot apply still fails the rebuild.
- A test that the skip list reaches the state object.
- `sm_mtnxzb5y_zpepqcpj` loads and claims on the buyer's device, OR runway 32
  carries a written finding explaining why it cannot and what would.
- Every chain-incomplete surface shows code + event id.

# BRIEF 2 — Do escrow events actually survive on the relays? (runway 32, part 2)

Everything in Brief 1 sits on an assumption nobody has tested: that a relay
keeps an escrow event. Chama's kinds (38100–38108) sit in the **addressable**
range (30000–39999), where a compliant relay keeps only the NEWEST event per
`(pubkey, kind, d-tag)` and drops the rest.

If two events in one chain ever share that triple, the older is deleted by
design, and every "the relays dropped that part of the chain" symptom in the
last month follows from it.

## Work

Write a script (not a UI) that, against the real community relay plus the
default pool: publishes a synthetic chain exercising every kind, including
two events of the same kind from the same author with the same `d` tag;
re-queries; and reports exactly what came back. Then answer in writing:

1. Which kinds can legitimately repeat per author per trade?
2. For each, does the current tag shape make them collide?
3. Does the community relay implement addressable replacement?
4. If collisions are real: change the tag shape (a per-event discriminator in
   `d`), or move the kinds out of the addressable range, or both — with a
   migration story for chains already published.

## Acceptance

- The script lives in `scripts/`, is runnable, and prints a verdict.
- The finding is written into runway 32 with the answers to all four
  questions.
- If a fix is needed, it is a separate brief with its own migration plan —
  do NOT change event kinds or tag shapes in the same pass that diagnoses
  them.

# BRIEF 3 — Notifications we can stand behind (runway 17) — hard mark

Two jobs, one lane. Ship together; do not let UnifiedPush land first.

## 3a. The quiet-sign-in law

`notifyLiveSinceRef` is set when the hook MOUNTS (page load), not when
hydration settles, and the freshness gate only asks whether a state's newest
signed moment is at or after that mark. So anything whose signed timestamp
lands in the hydration window can buzz although the user did nothing — Jet
gets "random notifications, just signed in".

Three specific suspects, in likelihood order:

1. The pre-lock on-chain ARBITER branch in `notificationForTransition` is the
   one path that deliberately fires with no `prev`. Pool membership alone
   (`BLF_OFFICIAL_ARBITERS`) currently qualifies someone, so every on-chain
   trade with a recent buyer join can summon an arbiter for a trade they
   never touched. Needs a real "seated or opted into THIS trade" gate.
2. `maybeNotifyNewListing` — correct, but lands in the same burst.
3. `maybeNotifyBuyerInterest` on a JOIN hold observed during hydration.

**The law:** nothing buzzes until hydration settles (or N seconds after
connect), and inside that window only a moment that is BOTH newer than
connect AND on a trade the viewer is a seated party to may fire. Everything
else is history, however freshly it arrived. Keep the `notifyDebug` trail so
a field report names its own cause.

## 3b. UnifiedPush + FCM (runway 2, promoted)

Closed-app delivery on the APK: UnifiedPush for de-Googled builds
(GrapheneOS is the reference device), FCM where Play services exist, using
the VPS wake path sketched in runway 2.

## Acceptance

- Pure tests for the quiet window: an event older than connect never fires; a
  newer event on a trade the viewer is not seated in never fires; a newer
  event on a seated trade fires once.
- A pool arbiter who is not seated and has not opted in receives nothing.
- A device with no Play services receives a push through UnifiedPush; a
  device with them receives one through FCM; neither fires for a hydration
  replay.

# BRIEF 4 — The arbiter record, where the decision happens (runway 21) — hard mark

Jet's framing, and it is right: buyers and sellers should read an arbiter's
proof of work BEFORE they commit, not meet a stranger at dispute time. The
roster and the "marketplace" are the same dataset; the missing surface is the
record rendered IN the trade at the moment of commitment.

## Work

1. **One derivation.** Pure `arbiterRecord(pubkey, escrows, bonds, ratings,
   nowSec)` → healings served, median response latency, disputes voted,
   ruling concentration (`arbiter-pattern.ts` already computes this), bond
   size + tenure (`bondTenureBlocks`, `tenureTier`), liveness
   (`computeChamaLiveness`). Chain-derived only. Nothing self-reported.
2. **In the trade view, above "agree & join"**: a compact card — who would
   arbitrate, bond, healings, median latency, disputes voted, last seen —
   expandable to the full record. Both sides, every vertical that seats an
   arbiter.
3. **On the Dashboard for bonded arbiters**: their own record, large and
   proud. It is what earns them selection, and watching it grow is the loop
   that keeps arbiters showing up.
4. **The roster view** reuses the same card as a list row.

## The copy rule, non-negotiable

This measures CONDUCT, never identity. It says what someone has done and what
they have at risk. It cannot say they are not the counterparty — that is what
the bond is for. No surface may imply otherwise (see runway 18 for why every
liveness/KYC ritual was rejected).

## Acceptance

- `arbiterRecord` is pure and tested, including the empty case (a new arbiter
  reads as new, never as good).
- The trade view shows it pre-commitment in every arbiter-seated vertical.
- No string in any of the four surfaces asserts identity.

# BRIEF 5 — The rich listing (runway 26)

A listing is one line (`description`) pretending to be a product page. Split
it: `title` (short, what cards show) + `body` (long, pasted, kept).

- **Formatting**: accept pasted text; keep paragraphs and line breaks; render
  a SAFE subset — paragraphs, breaks, lists, bold/italic, links.
- **Never render pasted HTML.** Parse to a small AST or markdown-ish subset.
  No `dangerouslySetInnerHTML` anywhere near this.
- **Links** render with the href VISIBLE, open in a new tab, carry
  `rel="noopener noreferrer nofollow"`.
- **No remote images.** A seller's image URL hands them every viewer's IP.
- **Length** generous (a few thousand chars); cards clamp a preview, the
  trade view shows all of it.

## Acceptance

- Pure `parseListingBody()` with tests: script tags, event handlers,
  `javascript:` URLs, data URLs and nested markup are all neutralised.
- A 3,000-character pasted description round-trips create → relay → other
  device → render.
- Cards stay one-line-ish; nothing reflows the Browse grid.

# BRIEF 6 — One attention surface (runway 31)

A user mid-trade can meet six orange/purple things on one screen: the ChamaBar
escrow pill, the ActiveTradePill, the attention card, a stranded-claim card,
the seller-queue tile and the needs-you badge.

**The law: ONE attention surface per screen, and it lives in the chrome.** The
escrow pill already glows from every tab and is tappable, so it is the home.

- Pill = the single live channel: "N active · X in escrow" / "N need you" /
  "recover X" — by priority, never stacked.
- The Me attention card becomes a plain list header, not a banner.
- Per-item urgency stays on the ITEM; never repeated in chrome.
- Colour means state, not importance: amber = your move, purple = money
  moving, green = done. **Two ambers on one screen is a bug.**

## Acceptance

- A pure priority function decides what the pill says, with tests for every
  combination (needs-you + active + stranded).
- A screenshot pass: no screen in the app shows two amber attention surfaces.

# BRIEF 7 — Small debts with real weight

Each is small, independent, and worth doing in this cycle.

**7a. `lts.resolvedRefunded` names the wrong party.** The trade room says
"Resolved — funds refunded to the seller" while the details panel computes
the party correctly. On a goods sale the buyer locks, so REFUND returns to
the BUYER. Use the party-aware string (`trade.nsRefundedBackTo`).

**7b. Adopt an existing kind-0 name.** A user who already has a Nostr profile
should see THEIR name prefilled in Profile, so Chama's publish extends their
identity instead of competing with it. Fetch own kind-0 at connect; when no
local name is set, adopt it.

**7c. Match results by settlement rail — finish it (runway 15).** Browse and
the canvas group by rail today. Verify the guided flow's rail question stays
in sync, and that no surface still renders a flat mixed list.

**7d. GIF / animated avatars.** Jet wants a custom, recognisable arbiter
identity. Accept animated formats where an avatar renders, with a size cap
and a static first-frame fallback. Never auto-fetch from a third-party URL
(see Brief 5's IP-leak rule) — same-origin or embedded only.

# BRIEF 8 — The merry-go-round: flip readiness (the finale)

`CHAMA_RING_WRITER_ENABLED` and `CHAMA_ROTATION_ENABLED` are both `false` in
`src/escrow-engine/experimental-escrow-features.ts`. The engine, the
deterministic-outcome law, the weekly race, the evidence-committed RESOLVE and
the full-cycle simulation are built and green. The flip is a FLEET decision,
not a code decision.

## Preconditions, all of which must be true and stated in writing

1. Brief 1 closed — a chain that will not replay is intolerable when a circle
   settles weekly for a group.
2. Brief 2 answered — if relays drop escrow events, rotation multiplies the
   blast radius by the number of seats.
3. Brief 3 shipped — rotation depends on people showing up on time; silent or
   random notifications break the whole social contract.
4. Enough of the fleet runs a 6.4.x reader with the evidence-committed
   RESOLVE that a flag-flipped writer cannot strand an older client.
5. A real cycle has run end-to-end in sim on more than one device, with the
   host locking last and a collection round completing.

## Then, and only then

Flip both flags in one release. Write the cycle-failure and sacrifice-round
rules into user-facing copy BEFORE the flip, not after. And keep the first
public circles small — a lost round is a story people tell for years.
