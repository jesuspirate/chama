# Brief — three surfaces that are telling you things that aren't so

From Jet's 2026-09-22 screenshots. All three are display-layer: no money is
at risk in any of them, and all three make Chama look like it knows something
it doesn't. Verified against `dd0f843d` (v6.4.7).

## A. The 2,501,999,295,746-hour countdown

Screenshot: *"for the seller to lock  2501999295746h 10m 30s"*.

That number is not garbage, it is a sentinel. Work it back:
`2501999295746 × 3600 + 630 = 9,007,197,464,686,000`, which is
`Number.MAX_SAFE_INTEGER` minus the current unix time. So `expiresAt` is
exactly `Number.MAX_SAFE_INTEGER`, and `CountdownTimer` is faithfully
rendering `expiresAt - now`.

Where it comes from: `state-machine.ts:533`, in `PLAN_START` —
`next.expiresAt = Number.MAX_SAFE_INTEGER;` with the comment that the parent
is now a persistent manifest, not a fundable listing. That is a correct use
of a sentinel meaning **never expires**.

Where it breaks: `preLockDeadline` (`src/ui/decisions.ts:2011`) reads

```ts
const listingAt = state.expiresAt > 0 ? state.expiresAt : null;
```

The guard only knows one convention for "no deadline" — zero. The sentinel
passes `> 0`, becomes a real listing expiry, and the surface renders a running
countdown. Note the function already handles the tranche case for *holds*
(`if (!state.tranchePlan)`) but computes `listingAt` unconditionally, so a
parent room falls straight through.

**Fix:** `preLockDeadline` returns `null` for a non-expiring listing. Treat
`Number.MAX_SAFE_INTEGER` as the named sentinel it is — give it a constant
(`NEVER_EXPIRES`) in the engine and have both sides import it, rather than
comparing magic numbers in two files.

**Belt and braces:** `CountdownTimer` should refuse to render an absurd
horizon. A deadline more than, say, a year out is not a countdown — render
nothing, or the untimed waiting copy. A UI component should not be able to
print a thirteen-digit hour count no matter what it is handed.

Add a test with `expiresAt = Number.MAX_SAFE_INTEGER` asserting
`preLockDeadline` returns null, and one asserting the timer renders nothing
past the horizon.

## B. The arbiter dashboard is watching trades you are a party to

Screenshot: Arbiter → WATCHING 2, both rows `B 12ab62… · S e2ae2b…`, where
`12ab62eb…028d` is Jet's own pubkey in the header. He is the **buyer** on both
trades, and they are in his arbiter watch queue.

`src/ui/screens/MeScreen.tsx:2658`:

```ts
const isPoolArbiter = trade.communityArbiters.some(pk => pk.toLowerCase() === lowerPubkey);
const isAssignedArbiter = role === Role.ARBITER;
const watchesAsArbiter = isAssignedArbiter || isPoolArbiter;
```

`isPoolArbiter` is true for **every trade in a community whose pool lists
you** — including every trade where you are the buyer or the seller. There is
no principal exclusion, so a pool member's watch queue fills with their own
trades.

This is wrong twice. It implies you might arbitrate a trade you are a party
to, which is exactly the structural separation runway 18 says the design
depends on. And it inflates the count, so a genuine trade needing a pool
backup is buried among your own.

**Fix:** a pool member watches only trades where they hold no principal seat.

```ts
const isPrincipal = role === Role.BUYER || role === Role.SELLER;
const watchesAsArbiter = isAssignedArbiter || (isPoolArbiter && !isPrincipal);
```

And if `isAssignedArbiter && isPrincipal` is ever true, that is a data fault,
not a queue entry — surface it loudly rather than watching it quietly.

Tests: a pool member who is the buyer sees zero watched trades; a pool member
who is neither party sees the trade; an assigned arbiter who is also a
principal produces the fault, not a silent watch row.

## C. Profile names are never cached, so every release looks like a reset

Jet: *"all the Nostr profile renames are not showing after a new release…
something is resetting it."*

Nothing is resetting it. `src/ui/App.tsx:954`:

```ts
const [nostrProfiles, setNostrProfiles] = useState<NostrProfileNameMap>({});
```

The resolved-name map is component state, initialised empty, and never
persisted anywhere. Every cold load starts at `{}` and re-fetches kind-0 from
relays for every counterparty. A release just guarantees a cold load, which
is why it looks release-shaped — but the same thing happens on any hard
refresh or evicted service worker. Until the fetch lands (or if it never
does, for a counterparty with no reachable kind-0), the generated pseudonym
is what you see.

**Fix:** cache the resolved map user-scoped, next to the other stores
(`src/storage/user-scope.ts`), keyed pubkey → `{ name, fetchedAt }`. Render
from cache on mount so names are correct in the first frame, then refresh in
the background and write back. Names are public kind-0 data, so caching them
carries no new privacy cost — but the cache must stay behind the existing
kind-0 toggle, and clearing the toggle must clear the cache, or the toggle
stops meaning anything.

While there: `KIND0_TOGGLE_KEY_PREFIX` writes
`chama_fetch_kind0_enabled_<pubkey>` through raw `localStorage`, not
`setScopedStorageItem` like the rest of the storage layer. Two identities on
one device share it. Small, and worth aligning in the same pass.

Tests: a populated cache renders names before any fetch resolves; turning the
kind-0 toggle off empties the cache; a cache miss still falls back to the
pseudonym rather than a blank.

## Not in scope, but decide it

The trade view shows *"Arbiter record · Gentle Fish · 0 sats — Healings: 5 ·
Disputes voted: 2 · Median response: 3765 min · Bond tenure (blocks): —"*.

Every figure there may be accurate, and the record rules in
`docs/v6.5-readiness.md` are being followed. But read it as a stranger about
to press Agree & Join: a bond of **0 sats** and a blank tenure sit beside
five healings and two votes, and the eye takes the activity as a credential.
62 hours of median response is presented as a neutral number. Worth deciding
whether a zero bond should lead rather than trail, and whether a response
time that long should be worded rather than counted. That is a copy and
ordering judgment, not a defect — Jet's call, not Codex's.
