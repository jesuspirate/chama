## LOCK publication — release blocker fixed (2026-10-03)

The fallback in `EscrowClient.lockEscrow` skipped publishing when no ecash
custody record was supplied, yet marked the local LOCK acknowledged. The
fix awaits `relayManager.publish` on that path. Sim, testnet and on-chain
locks use it; the durable ecash publish/retry path remains intact. Regression
`91fc134a` first appears in tag `v6.4.6` and remains through `v6.4.18`.

`lock-publish.tests.ts`, included in `npm test`, uses signed events, real
participant encryption and a simulated relay. It verifies live buyer delivery,
fresh-client replay, ecash voting, and rejection for sim, legacy ecash,
durable ecash and on-chain locks. Unacknowledged durable ecash remains saved
for retry. Typecheck, full npm tests and build passed for the publication fix.

### Older unsent locks: recovery is conditional

A warm funder session that still holds the signed LOCK can republish it on
explicit reopen: the completeness retry fetches full history and backfills
missing events to the preferred relay. The manual Re-broadcast action also
publishes the cached chain. The added regression verifies the original signed
LOCK is reused for sim and on-chain cases.

A fresh client with a LOCK only in the durable cache is different: if the relay
chain validly ends at CREATED, even `repairFromCache: true` does not consult
the disk cache. There is no unconditional heal-on-update guarantee. The
regression pins that limitation; the twenty-line publish fix does not change
cache/recovery policy. On-chain funder reconciliation can separately re-check
the committed deposit and publish a LOCK for an eligible CREATED trade. It
is subject to the existing funding and late-deposit gates. Refund eligibility
comes from the committed Bitcoin refund height, not a universal wall-clock
30-day guarantee. Preserve device state when investigating a real stuck trade.
