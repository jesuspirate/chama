# v6.4.10 brief 03 — Start the clock on 6.5 row 4: a client tag

Small, and time-sensitive only because its value is the weeks of relay data
it collects after it ships. Do it in the same pass as brief 01 Part 2.
Commit; don't push or ship.

## Why

`docs/v6.5-acceptance-protocol.md` row 4: Chama events carry no client or
version tag (`TAGS`, `src/escrow-engine/types.ts:205`), so nobody can tell
which Chama versions are reading the relays before the rotation flags
change what gets written. Option 1 there is the real fix: tag events now,
read the relays in a few weeks.

## Change

1. Add `CLIENT: "client"` to `TAGS`. Every escrow event Chama publishes
   (kinds 38100–38116, 38135) carries `["client", "chama", "<version>"]`,
   version from `__APP_VERSION__`, plus `"native"` / `"web"` / `"start9"` as
   a 4th element if the build already knows which it is (don't invent a new
   build switch for it).
2. Readers ignore it completely: not part of any signature-checked payload,
   not in the reducer, not in replay equality. A missing or odd client tag is
   never an error. Old events without it replay byte-identically.
3. Don't tag chat content or anything encrypted beyond the outer event.
4. `scripts/inspect-trade-relays.ts` (or a tiny new
   `scripts/probe-client-versions.ts`): count recent Chama events by
   client/version per relay, and "untagged" (= older than 6.4.10).

## Tests

A published CREATE/JOIN/LOCK carries the tag; the reducer output for a
chain with and without tags is identical; a malformed tag doesn't reject
the event.

## Row 4 after this ships

Record in `docs/v6.5-readiness.md`: option 1 chosen, date shipped, first
probe run date. Row 4 becomes answerable when the untagged share of recent
events is small enough for Jet to call it.
